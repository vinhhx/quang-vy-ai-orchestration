### 2. Child process with piped stdin and captured stdout (`curl -K -`)

### 4. `PRAGMA data_version` pump (`src/dashboard/pump.rs`)

`pump::spawn(db_path, hints: broadcast::Sender<i64>, stop: Arc<AtomicBool>) -> JoinHandle` (L10-14). Own thread `ab-pump`, own `db::open` connection, 250 ms tick (`TICK_MS`, L7):
```rust
let mut last_data_version: i64 = conn.pragma_query_value(None, "data_version", |r| r.get(0))?;
while !stop.load(SeqCst) {
    std::thread::sleep(Duration::from_millis(TICK_MS));
    let current_version: i64 = conn.pragma_query_value(None, "data_version", |r| r.get(0))?;
    if current_version != last_data_version {
        last_data_version = current_version;
        // SELECT run_id, MAX(id) FROM events WHERE id > ?1 GROUP BY run_id
        for (run_id, run_max_id) in runs { let _ = hints.send(run_id); }
        let _ = hints.send(0);
    }
}
```
Fan-out = `tokio::sync::broadcast::Sender<i64>` (capacity 1024); hint `run_id`>0 = new events of that run, `0` = "something changed" (also sent after `reconcile_stale_runs`, L58-70, and after every data_version change, L106). `AppState.hints` is the sender. **Subscriber point for the detector:** `st.hints.subscribe()` -> on each hint (debounce) re-scan tasks. Caveat: hints only follow DB changes of `events`/any write (data_version changes on ANY commit by another connection, including `tasks` updates from `claim::release`), so `hints.send(0)` fires for `auto_state='gate'/'stopped'/'done'` writes; but the pump does not carry task facts, so the detector must re-read via `db::open` + `load_task_state`-equivalent facts, and also run once at start (to seed dedupe without sending, "restart must not resend") and on a slow timer as a safety net (broadcast `Lagged` errors must trigger a full rescan). The pump's error pattern: `term::emit("Lỗi … trong pump: {e}")` then retry/break.

### 9. Test conventions and a fake Telegram

- Integration tests: `tests/*.rs` with `mod common; use common::Sandbox;`. `Sandbox::new()` (`tests/common/mod.rs` L47-100) creates tempdir with `home`, `xdg_config`, `xdg_data`, writes `brain_config.json`. `sb.command(args, extra_env)` (L278-302) clears nothing but sets `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `AGENT_BRAIN_DB`, `AGENT_BRAIN_CONFIG`, `GIT_CONFIG_*`, `FAKE_CLAUDE_*`; so a `telegram.json` written to `sb.xdg_config/agent-brain/telegram.json` (mode 0600) is automatically isolated from the real one. `sb.serve(extra_env) -> Serve` (L401-~490) spawns serve on port 0, parses the URL line (needs the first stdout line with `http://127.0.0.1:{port}/?token=…`), handshake, returns a handle with `get/post_json/stop(sig, timeout)`; stderr goes to `srv.stderr_path` (use it to assert the Telegram warning/status lines). `sb.db()` opens the DB; `wait_until(timeout, f)` (L657) is the polling helper.

Option (b) tests the real `curl` invocation and the "token not on argv" rule (assert via `/proc/<pid>/cmdline` of the real curl child or by recording argv in the stub). For a deterministic test of D-04 prefer (a) recording `argv` and asserting the token is absent.
- Reuse existing action-test patterns for gate/stop states: `tests/dashboard_autopilot.rs`, `dashboard_races.rs`, `dashboard_kill.rs` (kill confirmation analog), `autopilot_driver.rs`/`autopilot_kill.rs`.
- Cargo: `[dev-dependencies] tempfile` only; no HTTP crates (and `--offline --locked`). Pure-logic unit tests live in `#[cfg(test)] mod tests` inside the source file (e.g. `autopilot/claim.rs` L360-462, `view.rs` L143+).

## Notes for the planner (gotchas found while mapping)

1. `tests/common/mod.rs::serve` blocks on the dashboard URL line within 15 s; any slow Telegram start-up work must not run before that line is printed.
2. `JobManager::start` reserves a project and refuses a second job (`reservations`), and `busy_reason*` also reads `jobs.reserved()`: the bot's actions must use the SAME `Arc<JobManager>` held in `AppState.jobs`.
3. Autopilot jobs started by the bot print `Autopilot …` lines that `jobs.rs` L227-247 echoes to serve's terminal as `[job N] …`; keep that behavior (D-20 of 05.2).
4. `post_kill_run` refuses runs without a `task_id`; the bot's `Kill` button should do the same (message: reuse the existing Vietnamese text).
5. `cmd_kill` writes `request_auto_stop(.., "kill")` when a driver is alive, producing a `dung_boi_ban` stop that the detector will then notify; decide whether to suppress the stop message for a stop the user just caused via Telegram (mark the key as notified when the action succeeds, edit the original message with "Telegram đã Kill").
6. `AutoJson.stop` persists after `Dừng hẳn` (`end_autopilot` keeps `aj.stop` as history, `api_tasks.rs` L1771): detector keys must include `auto_state`, otherwise an ended task would re-notify.
7. Dashboard-sourced actions must also update the Telegram message ("who acted: Telegram or dashboard", D-15): detector sees the state change via the pump and edits the stored `message_id`; this argues for storing message ids (brain.db table) rather than memory only.
