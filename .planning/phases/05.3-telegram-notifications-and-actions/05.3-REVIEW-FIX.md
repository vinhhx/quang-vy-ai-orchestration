## Fixed Issues

### WR-01: `AGENT_BRAIN_TELEGRAM_API` loopback check can be bypassed with URL userinfo

**Files modified:** `agent-brain/src/telegram/transport.rs`
**Commit:** 14af603
**Applied fix:** New `is_loopback_http` accepts only `http://127.0.0.1:<port>` with an optional `/path`. The port must be 1 to 5 ASCII digits, parse as `u16`, and be non-zero. Userinfo (`@`), `127.0.0.1:80.evil`, `\`, `?`, `#`, spaces, empty port, port 0, port above 65535 and `+9` are all refused. `api_base` and `curl_argv` (the `--proto` choice) both use it. The `env_overrides` unit test keeps its old cases and now covers 12 bad overrides. A `curl_argv` case checks that `http://127.0.0.1:1@evil.example` gets `=https`.

### WR-02: `kill_run` verifies the confirmed run but kills "the task's running run"

**Files modified:** `agent-brain/src/dashboard/api_runs.rs`, `agent-brain/tests/dashboard_actions.rs`
**Commit:** 2179cc5
**Applied fix:** Before `runner::cmd_kill`, `kill_run` lists the task's `running` runs and refuses unless they are exactly `[run_id]`. The refusal reads "Task N có nhiều run đang chạy (run …) — không chắc dừng đúng run M, mở dashboard để xử lý". It signals nothing, and `cmd_kill` is still the only path (no new signalling under `src/telegram`). New tests: `kill_run_refuses_when_task_has_two_running_runs` (both runs stay `running`) and `kill_run_single_running_run_reaches_cmd_kill`.
**Note:** The check and `cmd_kill` are separate reads, so a run that starts in between can still race. The window is tiny and the result is the same refusal or lost mark as before. Passing the run id into `cmd_kill` would close it, but that changes the CLI-facing function, so I did not do it here.

### WR-03: Pressing a button on a message the bot can no longer read overwrites the message with only the result line

**Files modified:** `agent-brain/src/telegram/bot.rs`, `agent-brain/src/telegram/outbox.rs`, `agent-brain/tests/telegram_actions.rs`
**Commit:** 65901a2
**Applied fix:**
- `on_callback` takes the text from the tracked entry (new `Registry::text_of_message`) when the callback carries none.
- When no text is known either, the new `edit_result` sends the result as a reply to the pressed message and strips the old message's buttons. It never overwrites the message with only the result line.
- `edit` itself now sends a keyboard-only edit for an empty text.
- `send_prompt` omits an empty keyboard.
- All `with_suffix(&press.text…)` sites (`apply_outcome`, `stale`, the `perform_return` results, Kill ask, Kill result, Kill cancel) go through `edit_result`.

New tests: `press_without_text_keeps_tracked_text` and `press_without_text_untracked_sends_new_message`.

### WR-04: Result suffix can push an edit past Telegram's 4096-character limit

**Files modified:** `agent-brain/src/telegram/render.rs`, `agent-brain/src/telegram/bot.rs`, `agent-brain/src/telegram/detect.rs`
**Commit:** 2853dd5
**Applied fix:** New `render::with_suffix` clips a suffix longer than 1000 characters, then clips the original to `min(4096 - suffix length, MAX_TEXT)`. The bot's `with_suffix` delegates to it, and `detect::follow_tracked` (the moved-on edit) uses it too. The note shown in the `Trả về Lead` result line is cut to 80 characters plus `…` (`NOTE_EXCERPT`). The unit test `with_suffix_stays_within_telegram_limit` checks suffix lengths from 0 to 5000.

### WR-05: Bot is left half-running when the poll thread exits or fails to start

**Files modified:** `agent-brain/src/telegram/mod.rs`, `agent-brain/tests/telegram_outage.rs`
**Commit:** 615956b
**Applied fix:** `start()` sets the stop flag when the `ab-tg` thread cannot be spawned. `poll_thread` sets it when `getMe` fails with a non-retryable error, as the 401 branch already did. I did not change `is_unauthorized` to include 404, because the stop flag covers the problem and the 401 message names the 401 code. New test `getme_non_retryable_stops_notifications` (fake `getMe` returns 404, a new gate sends nothing).
**Note:** The spawn-failure branch has no automated test, because a thread-spawn error cannot be forced. The change is a single `stop.store`.

### WR-06: A load failure during detector seeding makes a restart resend an old event

**Files modified:** `agent-brain/src/telegram/detect.rs`, `agent-brain/tests/telegram_notify.rs`
**Commit:** 39fc886
**Applied fix:** I used the "seen-on-load" option. `seed` records a task that fails to load in a new `unseeded` set. The first scan that reads such a task marks its current event as seen without notifying, then drops it from the set (also on `Gone`). I did not make `seed` return an error and retry, because one permanently unreadable task (a corrupt row, for example) would then block notifications for every task. New test `unreadable_task_at_start_does_not_resend_old_event` corrupts a run row before serve starts, then repairs it, and expects no resend.
**Status:** fixed: requires human verification (logic-class finding). One accepted trade-off: an event that really is new, and arrives while the task is still unreadable, would be marked seen without a notification. Telegram offers no way to tell it from a pre-restart one.
