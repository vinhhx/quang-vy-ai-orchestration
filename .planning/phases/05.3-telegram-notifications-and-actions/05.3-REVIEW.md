The core security design holds up:
- The token only goes through curl stdin.
- `telegram.json` is 0600, with an atomic save.
- `authz` runs before anything else is read.
- Callback decoding is strict.
- Kill needs two presses.
- No inbound listener exists.

I found no BLOCKER. Six WARNING items remain:
- A claimed network guard that can be bypassed (verified with curl).

## Warnings

### WR-01: `AGENT_BRAIN_TELEGRAM_API` loopback check can be bypassed with URL userinfo

**File:** `agent-brain/src/telegram/transport.rs:26` (also `:146`)
**Issue:** The guard only checks `v.starts_with("http://127.0.0.1:")`. A value such as `http://127.0.0.1:1@evil.example/` passes. curl reads `127.0.0.1:1` as user:password and `evil.example` as the host. I confirmed this locally with `curl -v "http://127.0.0.1:1@localhost:9/…"`, which connects to `localhost:9`.

`curl_argv` uses the same prefix test to choose `--proto =http,https`. So the token is then sent in clear text to a non-loopback host. This contradicts the module comment ("the token never leaves the machine in clear text"), README line 190, and threat T-05.3-05. Exploiting it needs control of the serve environment, so I rate it WARNING, not BLOCKER. The check still does not do what its tests and docs claim. `env_overrides` has no case for it.

**Fix:** Parse the authority instead of using a prefix test.
```rust
fn is_loopback_http(v: &str) -> bool {
    match v.strip_prefix(LOOPBACK_HTTP) {
        Some(rest) => {
            let port = rest.split(['/', '?', '#']).next().unwrap_or("");
            !port.is_empty() && port.bytes().all(|b| b.is_ascii_digit())
        }
        None => false,
    }
}
```
Use `is_loopback_http` in `api_base` and in `curl_argv`. Add unit cases for `http://127.0.0.1:1@evil.example` and `http://127.0.0.1:80.evil.example`.

### WR-02: `kill_run` verifies the confirmed run but kills "the task's running run"

**File:** `agent-brain/src/dashboard/api_runs.rs:75-100` (with `agent-brain/src/db.rs:564`, `agent-brain/src/runner.rs:55-70`)
**Issue:** `kill_run(run_id)` checks that `run_id` exists, belongs to a task and is `running`. It then calls `runner::cmd_kill(ctx, task_id)`. `cmd_kill` looks up `running_run_for_task(task_id)`, a `SELECT … WHERE status='running'` with no `ORDER BY`, and takes the first row.

If a task ever has two `running` rows, for example a stale row of a dead process next to a live run, the process killed or marked lost is not the run the user confirmed. The success text still says `Đã dừng run {run_id}`. Both the dashboard and the bot (T-05.3-10, rated high) rely on `run_id` binding, and that binding is not enforced. In the stale-row case the failure is "refused / marked lost", but the real run is not stopped and the audit line is wrong.

**Fix:** Bind the kill to the run, either by checking after the lookup or by passing the run id down.
```rust
// in kill_run, before cmd_kill
if let Some(r) = crate::db::running_run_for_task(&conn, task_id)? {
    if r.id != run_id {
        return Ok(KillOutcome::Refused(format!(
            "Task {task_id} có run {} đang chạy khác run {run_id} — mở dashboard để xử lý", r.id)));
    }
}
```
Better, give `cmd_kill` an optional `run_id` and add `ORDER BY started_at DESC, id DESC` to `running_run_for_task`.

### WR-03: Pressing a button on a message the bot can no longer read overwrites the message with only the result line

**File:** `agent-brain/src/telegram/bot.rs:437-445` (`Press.text`), used at `:686`, `:809`, `:858`, `:1032`, `:1046`
**Issue:** `Press.text` comes from `callback_query.message.text` and defaults to `""` when absent. The Bot API sends `MaybeInaccessibleMessage` (only `chat`, `message_id`, `date = 0`, no `text`) for messages that are no longer available to the bot, including old ones. The most important case is a gate message that waited a long time for approval. `authz` accepts it, because `chat.id` is present.

Every edit built with `with_suffix(&press.text, …)` then replaces the whole message with `"\n\n✓ Đã duyệt plan …"`. The Kill confirmation uses `base = press.text` and has the same problem. The plan summary, the buttons' context and the result are then gone from the chat. The registry entry, `removed.text` in `act` and `on_kill`, still holds the original text, but it is not used.

**Fix:** Take the text from the tracked entry when the press carries none.
```rust
let text = press_text.filter(|t| !t.is_empty())
    .or_else(|| removed.as_ref().map(|t| t.text.clone()))
    .unwrap_or_default();
```
In `on_callback`, keep `Press.text` as `Option<String>`. In `apply_outcome`, `on_kill` and `perform_return`, fall back to `Tracked.text` (or `PendingNote.origin_text`). If neither is available, send the result as a new message instead of editing.

### WR-04: Result suffix can push an edit past Telegram's 4096-character limit

**File:** `agent-brain/src/telegram/bot.rs:948-950` (`with_suffix`), `:679` (note text in suffix); `agent-brain/src/telegram/render.rs:13` (`MAX_TEXT = 3900`)
**Issue:** `with_suffix` clips the original message to 3900 characters and appends the suffix. That leaves only about 196 characters for the suffix. The suffix can be far longer. `Đã trả về Lead (ghi chú: «{n}»)` carries a note of up to 500 characters (about 560 characters in total). `\n\n{msg}` on a Kill refusal carries an arbitrary `cmd_kill` error. For a message longer than about 3.5k characters, `editMessageText` fails with 400 "message is too long". The outbox drops it as non-retryable, which logs `bỏ sửa tin`. The message then keeps its buttons even though the action already ran. The same arithmetic applies to the detector's moved-on edit (`t.text + suffix`).

**Fix:** Clip the combined text, not just the original.
```rust
fn with_suffix(original: &str, suffix: &str) -> String {
    let room = TELEGRAM_MAX.saturating_sub(suffix.chars().count()); // 4096
    format!("{}{suffix}", render::clip(original, room.min(render::MAX_TEXT)))
}
```
Also clip the note inside `what` (for example to 80 characters), or leave the note out of the edit. Apply the same helper in `detect::follow_tracked`.

### WR-05: Bot is left half-running when the poll thread exits or fails to start

**File:** `agent-brain/src/telegram/mod.rs:171-177` and `:217-221`
**Issue:** `outbox::spawn` and `detect::spawn` start before the `ab-tg` thread. Two exits leave them running with nothing to stop them:
1. If spawning `ab-tg` fails (`:171-177`), `start()` returns `None` without setting `stop`. The sender and detector keep running and keep sending notifications. Nobody can stop them, because no `BotHandle` was returned.
2. If `getMe` fails with a non-retryable error (`:217-221`, for example 404 for a malformed or deleted token), `poll_thread` prints a line and returns. It does not set `ctx.stop`, which the 401 branch does. The detector and outbox continue. Every later event is queued, tried, rejected with a 4xx and logged as `bỏ tin cho task N`, while buttons never work. The user sees "Telegram: lỗi" once and then noise.

**Fix:** Set the stop flag in both places.
```rust
if let Err(e) = spawned { stop.store(true, Ordering::SeqCst); … return None; }
// poll_thread, None arm:
crate::term::emit(&format!("Telegram: lỗi — {}", e.text()));
ctx.stop.store(true, Ordering::SeqCst);
return;
```
Treat 404 like 401 in `CallError::is_unauthorized`, because `setup::call_failed` already treats them the same.

### WR-06: A load failure during detector seeding makes a restart resend an old event

**File:** `agent-brain/src/telegram/detect.rs:211-226` (`seed`), `:265-269` (`scan`)
**Issue:** `seed` only records `seen` and the signature for tasks that load successfully. On `Eval::Failed` (a transient DB or git read error at start-up) it records nothing. The first `scan` then sees a changed signature, loads the task and finds an event that is not in `seen`. It emits `Notify`, so a gate, stop or QA message that existed before the restart is sent again. This breaks TELE-04 ("restart does not resend"). The window is small but real, and the failure is silent.

**Fix:** Retry the seed for failed tasks before the first scan.
```rust
// seed(): collect failed ids and retry a few times (or return Err so `run` retries the whole seed)
Eval::Failed => return Err(BrainError::error(format!("không đọc được task {task_id} khi khởi động"))),
```
`run()` already retries `seed` every second and logs the error once.

## Info

### IN-01: `callback::decode` accepts non-canonical ids

**File:** `agent-brain/src/telegram/callback.rs:76-82`, doc at `:88`
**Issue:** The doc says "anything not produced by `encode` returns `None`", but `a:007:<rev>` decodes to task 7 (leading zeros are accepted). It is harmless, because the rev check still gates the action, but the contract and the tests (`rejects_other_shapes`) do not match.
**Fix:** In `parse_id`, reject a leading `0` when `s.len() > 1`, and add `"a:01:<rev>"` to `rejects_other_shapes`.

### IN-02: Pairing loop makes back-to-back zero-timeout calls in the last second

**File:** `agent-brain/src/telegram/setup.rs:255-261`
**Issue:** When under 1000 ms remain, `left_secs` is 0, so `timeout = LONG_POLL_SECS.min(0) = 0`. `getUpdates` returns at once and the loop repeats until `expired()`. That is a few unneeded HTTPS calls, and a risk of a 429 at the end of the window.
**Fix:** If `left_secs == 0`, sleep the remaining milliseconds (or `break` into the expiry message).

### IN-03: `telegram setup` leaves lock info that makes a concurrent `serve` print a wrong URL

**File:** `agent-brain/src/telegram/setup.rs:186`
**Issue:** `write_info(std::process::id(), 0, …)` writes port 0. A `serve` started during pairing prints `agent-brain serve đã chạy (pid N) tại http://127.0.0.1:0/ …` (`dashboard/mod.rs:116`), which is misleading.
**Fix:** In `mod.rs`, when `port == 0` or missing, print "đang chạy `telegram setup`" instead of a URL, or write `null` for the port.

### IN-04: Kill confirmation text can outlive its buttons

**File:** `agent-brain/src/telegram/bot.rs:801-817`, `agent-brain/src/telegram/detect.rs:163-177`
**Issue:** The first `Kill` press edits the message to "…Xác nhận Kill run N?" with Kill/Huỷ buttons, but the registry entry keeps the original text and keyboard. If the run ends or restarts before the user decides, `follow_tracked` swaps the keyboard (a `Keyboard` edit) and leaves the question text. The message then asks about run N with unrelated buttons. The tracked keyboard also hides the new keyboard from the "changed?" comparison.
**Fix:** Store the confirm text and keyboard in the `Tracked` entry on `KillAsk`, or, when the detector refreshes a message whose tracked text was altered by the bot, re-send the full text with the keyboard.
