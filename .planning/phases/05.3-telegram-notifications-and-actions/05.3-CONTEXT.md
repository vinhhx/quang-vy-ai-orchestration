# Phase 05.3: Telegram Notifications and Actions - Context

**Gathered:** 2026-10-21
**Status:** Ready for planning

<domain>
## Phase Boundary

The user gets a Telegram message when a task needs them, and can act on it from the message.

**Events that notify** (fixed by ROADMAP):
- waiting for plan approval (the Bạn gate);
- autopilot stopped, with its reason;
- QA passed;
- a run failed.

**Buttons** (fixed by ROADMAP and PROJECT.md):
- `Duyệt plan`;
- `Trả về Lead` (with an optional note);
- `Chạy thêm 1 vòng`;
- `Dừng hẳn`;
- `Kill`, which asks for confirmation first.

**Constraints:** the bot uses long polling, so no port is opened on the machine. Only the user's paired chat ID is accepted. No new tasks can be created from Telegram, and the dashboard is not reachable remotely. This is the narrow exception to the localhost-only rule recorded in `.planning/PROJECT.md` (Out of Scope).

**Out of scope:** new tasks from Telegram, remote dashboard access, desktop notifications, the work board (Phase 05.4), draft PR (Phase D).
</domain>

<decisions>
## Implementation Decisions

### Carried forward (locked, not re-asked)
- **D-01:** Telegram is a narrow exception to the localhost-only rule. It covers notifications and gate/stop actions only, and works through long polling with a chat-ID allowlist (user decision 2026-10-20, PROJECT.md).
- **D-02:** Every action goes through the same code paths and safety rules as the dashboard buttons:
  - Kill only through `runner::cmd_kill`;
  - one run per project;
  - one `personal` run at a time;
  - approval tied to the exact plan commit (05.2 D-28);
  - approval continues autopilot only while autopilot is on (05.2 D-15 amendment).
- **D-03:** Telegram copy is Vietnamese and uses the 05.1/05.2 status and stop-reason vocabulary (`hết vòng`, `hết ngân sách`, `vi phạm giao thức`, `vướng mắc`, `dừng bởi bạn`, `run lỗi`).

### HTTPS client
- **D-04:** agent-brain calls `api.telegram.org` by spawning the **system `curl`** as a child process. No new crate is added, and the `--offline --locked` build stays as it is. The bot token must never appear on curl's argv, where `ps` would show it. Pass the URL and token through stdin or a curl config read from stdin (`-K -`). If `curl` is missing, the bot does not start and serve prints a Vietnamese error. — **Reversibility:** reversible — swapping in a Rust HTTP crate later only touches the transport module.
- **D-05:** When Telegram is unreachable (no internet, API error, 429), the bot retries quietly:
  - backoff from 5 s up to 60 s;
  - notifications are queued and sent when the connection is back;
  - a queued notification whose task state has already moved on is dropped;
  - one warning line goes to the serve terminal.
  Agent work and autopilot never block on Telegram.

### Bot process
- **D-06:** The bot runs **inside `agent-brain serve`** and starts only when Telegram is configured. Without the config, serve behaves exactly as today. It detects events from brain.db changes through the existing pump (`PRAGMA data_version`). It runs actions through the same handlers or job code as the dashboard POST routes, so it gets the same busy rules and PDEATHSIG children. No Telegram works while serve is not running; this is accepted.
- **D-07:** Notifications cover **every** task that reaches a gate or stop while serve runs, including tasks driven by `agent-brain auto` in a terminal. The source is the database, not who started the task.

### Setup and secrets
- **D-08:** The token and the allowed chat ID live in `~/.config/agent-brain/telegram.json`, created with mode 0600. Serve refuses to start the bot, with a Vietnamese error, if the file is group- or world-readable. `config.json` stays free of secrets. The file must never be logged, printed, or included in diagnostics. — **Reversibility:** reversible.
- **D-09:** Pairing works through `agent-brain telegram setup`:
  1. It asks for the bot token, without echoing it.
  2. It prints a 6-digit code.
  3. The user sends that code to the bot.
  4. The command stores the chat ID of the sender of the code and confirms in the terminal and in Telegram.
  The code expires (Claude's discretion, around 10 minutes). Re-running setup replaces the pairing.
- **D-10:** Messages and button presses from any chat ID other than the paired one are **ignored silently**: no reply, and one serve-terminal line with the unknown chat ID. Callback queries from other chats are also refused.

### Messages and actions
- **D-11:** **Gate message.** It shows the task, project, profile, branch, plan title, the plan's `Thay đổi` file list, and the plan-review verdict and round. The current `.plan.md` is **attached as a document** so it can be read in full on the phone. Buttons: `Duyệt plan`, `Trả về Lead`, `Kill`. Kill appears only when a run is active.
- **D-12:** **Stop message.** It shows the stop reason and detail, as on the 05.2 amber banner. Buttons: `Chạy thêm 1 vòng`, `Trả về Lead` where 05.2 offers `Chạy lại Lead`, `Dừng hẳn`, and `Kill` if a run is active. A **QA passed** message and a **run failed** message carry the task summary. They show only the buttons that apply to that state.
- **D-13:** **`Trả về Lead` note.** After the button press, the bot asks for a note. The user's next text message becomes the note (05.2 D-17), or the user presses `Không ghi chú`. The prompt times out after about 10 minutes with no action taken.
- **D-14:** **`Kill` needs a second confirmation.** The bot edits the message to `Xác nhận Kill run {id}?` with `Kill` / `Huỷ`. Only the confirmation calls `cmd_kill`.
- **D-15:** **Stale buttons.** Before acting, the bot re-checks the task's current state, including the plan commit for approval. If the message is stale, the bot does nothing and answers `Task đã đổi trạng thái: …`. It then removes the buttons from that message. Every completed action edits its message to show the result and who acted (Telegram or dashboard).
- **D-16:** Tasks from **all profiles** (work and personal) notify, and each message shows the profile.

### Process
- **D-17:** Claude plans and reviews; agy executes (CLAUDE.md). Two exceptions follow the user's earlier approvals:
  - Claude may execute while the agy quota is out, until 2026-10-24.
  - `--dangerously-skip-permissions` for agy needs a fresh approval for this phase.
  Live checks against the real Telegram API need the user's own bot token and phone. Keep them in the final plan as user checkpoints. Automated tests use a fake Telegram (a local HTTP stub the curl transport points at, or a fake `curl`), never the real API.

### Claude's Discretion
- Message wording and layout beyond what is named here, and the callback-data format (it must be short, at most 64 bytes for Telegram, and must not be guessable as an action on another chat).
- `getUpdates` long-poll timeout, offset persistence, and how notification dedupe state is stored: a table in brain.db (needs a migration) or an in-memory set rebuilt on start. Whichever is chosen, restarting serve must not resend old notifications.
- Whether serve's start-up line and the dashboard show a Telegram status (`Telegram: đã kết nối` / `tắt` / `lỗi`). Recommended: one terminal line; a dashboard indicator is optional.
- The module layout (`src/telegram/…`) and how bot actions call the existing handlers: extract shared action functions from `api_tasks.rs` rather than duplicating them.
- Whether `agent-brain telegram test` (send a test message) exists alongside `setup`.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **Dashboard action handlers** in `api_tasks.rs` already implement every button (approve, return with note, auto on/stop, more-round, end) with the busy and state checks. The bot should call the same logic, factored into shared functions, not re-implement it.
- **Pump** (`dashboard/pump.rs`) already turns brain.db changes into live updates. It is the natural trigger for notification detection.
- **Task state derivation** (`taskstate.rs` `derive_with`, `autopilot/view.rs`) gives the gate and stop state and the reason text that messages need.

### Established Patterns
- Offline static build, `--offline --locked`, and no new crates without approval. D-04 avoids a crate entirely.
- Child processes use PDEATHSIG. Never `pkill`; stop processes by recorded PID only.
- Vietnamese user-facing copy. Errors name the problem and the file or key.
- Tests use fakes (`tests/fakes/fake_claude.py`). Live checks run only in the final plan, under the Phase 5 live-check rules.

### Integration Points
- `cmd_serve` starts the bot task when `telegram.json` exists and is valid.
- New CLI subcommand: `agent-brain telegram setup` (and optionally `test`).
- Possible migration for notification and dedupe state and the update offset (Claude's discretion).
</code_context>

<specifics>
## Specific Ideas

- The user approves plans from the phone. The attached `.plan.md` is the main reading surface, so the gate message itself stays short.
- The connection between this machine and Telegram must be outbound only. Nothing listens on a public port.
</specifics>
