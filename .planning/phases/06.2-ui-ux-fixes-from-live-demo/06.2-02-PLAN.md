# Plan 06.2-02: Telegram menu showing bot info and status

Phase 06.2, plan 2. Requested by the user: the Telegram bot was not running and nothing in the dashboard says why. Add a "Telegram" menu entry that shows the bot's information and status.

## Problem
`telegram::start` (agent-brain/src/telegram/mod.rs) returns `None` silently when `~/.config/agent-brain/telegram.json` is missing, and prints a single terminal line on other errors. The dashboard has no Telegram status at all (no API, no screen), so a stopped bot looks the same as a working one.

## Goal
A new read-only "Telegram" screen in the left sidebar shows whether the bot is off, misconfigured, starting, running or disconnected, with its basic info, and tells the user what to do when it is off. It refreshes by itself while open.

## Files in scope (touch nothing else)

- `agent-brain/src/dashboard/api_telegram.rs` (new) and `agent-brain/src/dashboard/mod.rs` (register the route, one line)

## Design
Status store: a process-global `static` in `telegram/status.rs` (a `OnceLock<Mutex<…>>`), not a new `AppState` field, so no existing `AppState` constructor changes. Snapshot fields: `state` (`off` | `error` | `starting` | `running` | `degraded`), `message` (Vietnamese reason, only for `error`/`degraded`), `bot_username` (from the first successful `getMe`, else null), `chat_id`, `paired_at`, `last_ok_at`, `outbox_pending`, plus, computed in the handler, `tasks_today` and `tasks_per_day_limit` (reuse the existing OD-2 daily counter in `telegram/intake.rs`; do not reimplement it) and `config_path` (the path string only).
- `off`: `telegram.json` missing (today `start` returns `None` for `LoadError::Missing`).
- `error`: file present but insecure, invalid, or curl/api-base check failed (today's `term::emit` cases); `message` is the same Vietnamese text already produced by `LoadError::message` / the error.
- `starting`: bot threads spawned, no successful `getMe` yet.
- `running`: `getMe` ok and `Health` not failing. `degraded`: `Health::is_failing()`.
- `GET /api/telegram` behind the existing token auth, `200` always, JSON of the snapshot. It must NEVER contain the bot token, any part of `telegram.json` other than chat_id/paired_at, or any URL containing the token.

Screen (`#/telegram`, nav label `Telegram`, title `Telegram`), Vietnamese copy, read-only (no token input in the browser, no buttons that change the bot):
- status badge with words `Chưa cấu hình` (off), `Lỗi cấu hình` (error), `Đang khởi động` (starting), `Đang chạy` (running), `Mất kết nối` (degraded); colour classes consistent with the readiness badges in `js/settings.js`
- rows (shown only when there is data): `Bot: @{username}`, `Chat ID`, `Đã ghép cặp lúc`, `Lần liên lạc thành công gần nhất`, `Tin chờ gửi: {n}`, `Task giao qua Telegram hôm nay: {n}/{limit}` (limit 0 shown as `không giới hạn` only if that is what the config means; read `config.rs` first), `Tệp cấu hình: {path}`
- when `off`: text `Bot Telegram chưa bật. Chạy "agent-brain telegram setup" trong terminal để ghép cặp bot, rồi khởi động lại agent-brain serve.` and a `Sao chép lệnh` button only if the app already has a copy-to-clipboard helper to reuse (grep `Sao chép` in js/); otherwise show the command as selectable text
- when `error`/`degraded`: the `message` text verbatim in the existing alert style
- refresh by polling `GET /api/telegram` every 5 s while the screen is open; stop the timer when the route changes (copy the cleanup pattern of an existing screen that polls; read `js/stats.js`, `js/overview.js`, `js/app.js` first); show the existing "mất kết nối" banner behaviour if the fetch fails, do not invent a new one
- Alpine CSP build only: no inline expressions beyond what the other screens already use, no `style=`, no `x-html`; all classes must pass `scripts/dashboard-ui-lint.sh`
