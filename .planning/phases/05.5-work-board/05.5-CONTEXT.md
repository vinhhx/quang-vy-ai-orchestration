# Phase 05.5: Work Board - Context

**Gathered:** 2026-10-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Dashboard v2 **step C, first half**: a new read-only screen `#/board` that shows a GSD project's plans as a dependency board. Plans are laid out in waves, with dependency lines, a highlighted critical path, click-to-focus on an item's chain, a side panel for the selected item, and a switch that collapses done items.

The data is read **live from the project's GSD files** (`.planning/ROADMAP.md`, `.planning/STATE.md`, `.planning/phases/*/*-PLAN.md` front matter, `*-SUMMARY.md` presence). Nothing is stored in `brain.db` and there is no schema change.

Out of scope for this phase (deferred, see `<deferred>`): Lead `--epic` mode and `.epic.md`, the `epics` / `items` / `item_deps` tables, manual add/edit of items and dependencies, starting an item as an agent-brain task, and live statuses for running/review items.

**Note for the roadmap:** the ROADMAP.md `Notes` line for 05.5 ("Tầng mới trên task: bảng `epics`, hạng mục, phụ thuộc") describes the full design. This phase deliberately ships only the live-read part (D-05). The planner should update that Notes line and define requirement IDs `BOARD-01…` in REQUIREMENTS.md.
</domain>

<decisions>
## Implementation Decisions

### Scope
- **D-01:** Phase 05.5 = board + GSD import only. Read-only board, no write actions, no new POST routes.
- **D-02:** A project has a board when its registered folder (from `projects_map.json`) contains `.planning/ROADMAP.md`. Every other project (no roadmap, `media` type, missing folder) shows an empty state in Vietnamese that says the board reads a GSD roadmap and names the expected path. There is no opt-in list.

### What an item is
- **D-03:** **One GSD plan = one board item.** The item key is the plan id (`05.4-03`), the title comes from the plan (objective / first heading; the planner picks the exact source), and edges come from front-matter `depends_on`. **One GSD phase = one epic** (epic filter). A roadmap phase with no plan files yet shows as a single placeholder item (key = phase number, status from the roadmap checkbox), so the graph has no holes.
- **D-04:** Status comes **only from GSD files**:
  - `xong`: the plan's `*-SUMMARY.md` exists. For a placeholder phase item, the roadmap checkbox is `[x]`.
  - `sẵn sàng`: not done, and every dependency is done.
  - `bị chặn`: not done, and at least one dependency is not done.
  - No `đang chạy` / `đang review` / `cần bạn` for imported items, because GSD runs outside agent-brain. Use the design-ref status vocabulary (glyph + color + word) for the three statuses that do apply.
- **D-04b:** Milestone filter = GSD milestone (from ROADMAP.md / its milestone sections). When the project has only one milestone, the filter control hides itself.

### Data path
- **D-05:** `GET /api/board?project=&epic=&milestone=` (token-gated like every route) **parses the project's `.planning/` files on each request**. No `brain.db` tables, no migration, no import command. Apply caps on file size, file count and parse time so a huge or hostile repo cannot stall `serve`. Read only inside the project's `.planning/` and do not follow symlinks out of it (the same path-safety stance as existing project reads). — **Reversibility:** reversible — epic mode later adds tables behind the same response shape.
- **D-06:** Refresh happens when the board screen opens and when the user presses **Đọc lại**, the same pattern as the workflows list on Dự án. No polling and no file watcher. The `brain.db` pump does not see file changes anyway.
- **D-07:** Bad data never blanks the board. Skip only the broken part (bad front matter, a `depends_on` that names an unknown plan, a dependency cycle, unreadable file) and list each problem in an amber warning box **`Dữ liệu GSD có lỗi`** with the file path and a Vietnamese reason. This mirrors the `workflows.json có lỗi` box.

### Waves, critical path, cross-phase
- **D-08:** Waves are **computed from the edges**: wave = longest dependency path from a root, as in the design-ref mockup. The front-matter `wave:` number is **not** used for layout. When it disagrees with the computed wave, add a warning line under D-07, but do not move the item.
- **D-09:** Critical path = the longest chain of **unfinished** items, **unit weight** (each unfinished item counts 1, done items count 0), using the same algorithm as the mockup. Ignore `estimate.tokens`. Draw it as yellow lines only (design ref).
- **D-10:** Cross-phase edges: the roadmap's `Depends on: Phase X` links phase X's sink plans (plans nothing else in X depends on) to this phase's root plans (wave 0), so `Mọi epic` gives one connected graph with one critical path. Explicit cross-phase `depends_on` in front matter (e.g. `[05-04]`) is honoured as is. **The default view is the current phase** (from `STATE.md` `current_phase`, with a fallback to the first phase that is not done) to keep the board small. `Mọi epic` is an explicit choice.

### Interaction
- **D-11:** The done-items switch is **"Thu gọn mục đã xong"**, **on by default**. A wave where every item is done collapses to a narrow column (`Wave N · 5/5 ✓`). Done items in mixed waves become one-line chips. Edges into collapsed items stay visible so dependencies still read correctly. Turning the switch off shows full cards.
- **D-12:** Clicking an item: 2px cyan ring, its whole upstream and downstream chain lit, unrelated items dimmed (design ref). A **read-only side panel** shows the key, title, phase (epic), milestone, computed wave, status, `requirements`, the "Phụ thuộc" and "Được chờ bởi" lists (each entry clickable to move focus), and the `PLAN.md` path relative to the repo. It does not show the plan body. Keyboard: items are focusable, Enter/Space selects, Esc clears focus and closes the panel.

### Carried forward (locked in earlier phases — do not re-decide)
- Stack and design rules from 05.1 D-07: Tailwind v4 standalone build (`scripts/build-css.sh`), Alpine CSP build, no CDN, offline, Vietnamese copy, light and dark themes, 05-UI-SPEC typography and banned classes, and `scripts/dashboard-ui-lint.sh` must pass.
- Status vocabulary from 05.1 D-08 and the design ref (one set across views). Board component specs come from the design ref "Components" table (board item, wave column 214px, dependency edge, legend) and "Layout and density". The board scrolls sideways inside its own container. The page body never scrolls sideways.
- Security: `127.0.0.1` plus a startup token, with the same auth middleware and headers as every route.
- Process: Claude plans and reviews. Execution uses agy per CLAUDE.md, or gsd-executor if agy quota is still out (the user chose gsd-executor in 05.4). Confirm at execute time.

### Claude's Discretion
- How plan front matter is parsed. The crate has no YAML dependency, and `src/report.rs::front_matter` is a flat parser. A small subset parser for `wave`, `depends_on`, `requirements` and title is preferred over adding a crate. If research recommends a crate, it needs the usual legitimacy checkpoint.
- The exact cap values, the response JSON shape, edge routing geometry, the side panel layout and breakpoints, where the `#/board` entry sits in the nav, and whether Tổng quan links to it.
- Whether a profile filter exists for imported data (projects carry a profile; the design-ref `profile=` param may filter projects).
</decisions>

## Existing Code Insights

### Reusable Assets
- `api_workflows.rs` and the Dự án workflows list: a read-only list re-read from a file on demand, with a Vietnamese per-line warning box. This is the same shape the board needs (D-06, D-07).
- `api_projects.rs`: resolves a project id to its folder and type, and already handles missing folders.
- `report.rs::front_matter`: a starting point for the front-matter subset parsing.
- The 05.1 shared status maps and formatters in `js/app.js` (glyph, color class and word per status).

### Established Patterns
- Every screen is `screens/<name>.html` plus `js/<name>.js`, using Alpine CSP components (no inline expressions beyond what the CSP build allows, object-form `:style`).
- Every GET is token-gated by the shared middleware and uses the same security headers. Error copy is Vietnamese.
- Tests are behavioural (the user does not read Rust). Each derivation rule (waves, critical path, cross-phase linking, status, warnings) needs a fixture-driven test, like `pipeline::derive`'s rule battery in 05.1.

### Integration Points
- A new `GET /api/board` in `dashboard/mod.rs`, a new `#/board` route plus a nav entry in `app.js`, and a new `screens/board.html` + `js/board.js`.
- The `app.css` rebuild after adding classes (the SVG edge colors, the dim state, the cyan ring).
</code_context>

<deferred>
## Deferred Ideas

- **Lead epic mode** (`agent-brain run lead PROJECT "…" --epic` → `.epic.md` reviewed like a plan → items created): a later phase (the second half of step C).
- `epics` / `items` / `item_deps` tables in `brain.db`, with cycle rejection on insert: with epic mode.
- Manual add/edit of items and dependencies on the board (`POST /api/items`, `PUT /api/items/{id}`): with epic mode.
- **Start an item as a task** (`POST /api/items/{id}/start`) and live item statuses (`đang chạy`, `đang review`, `cần bạn`) from a linked task: with epic mode.
- A "đang làm" status from git activity (plan commits without a SUMMARY): rejected for now in favour of GSD files only.
- Critical path weighted by `estimate.tokens`: rejected for now (estimates are often missing or low-confidence).
- Polling or a file watcher for live board refresh: rejected for now in favour of **Đọc lại**.
</deferred>
