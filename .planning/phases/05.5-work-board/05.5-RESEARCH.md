## User Constraints (from CONTEXT.md)

### Locked Decisions

### Scope
- **D-01:** Phase 05.5 = board + GSD import only. Read-only board, no write actions, no new POST routes.
- **D-02:** A project has a board when its registered folder (from `projects_map.json`) contains `.planning/ROADMAP.md`. Every other project (no roadmap, `media` type, missing folder) shows an empty state in Vietnamese that says the board reads a GSD roadmap and names the expected path. There is no opt-in list.

### What an item is
- **D-03:** **One GSD plan = one board item.** The item key is the plan id (`05.4-03`), the title comes from the plan (objective / first heading; the planner picks the exact source), and edges come from front-matter `depends_on`. **One GSD phase = one epic** (epic filter). A roadmap phase with no plan files yet shows as a single placeholder item (key = phase number, status from the roadmap checkbox), so the graph has no holes.
- **D-04:** Status comes **only from GSD files**:
  - `xong`: the plan's `*-SUMMARY.md` exists. For a placeholder phase item, the roadmap checkbox is `[x]`.
  - `sẵn sàng`: not done, and every dependency is done.
  - `bị chặn`: not done, and at least one dependency is not done.
  - No `đang chạy` / `đang review` / `cần bạn` for imported items, because GSD runs outside agent-brain. Use the design-ref status vocabulary (glyph + color + word) for the three statuses that do apply.
- **D-04b:** Milestone filter = GSD milestone (from ROADMAP.md / its milestone sections). When the project has only one milestone, the filter control hides itself.

### Data path
- **D-05:** `GET /api/board?project=&epic=&milestone=` (token-gated like every route) **parses the project's `.planning/` files on each request**. No `brain.db` tables, no migration, no import command. Apply caps on file size, file count and parse time so a huge or hostile repo cannot stall `serve`. Read only inside the project's `.planning/` and do not follow symlinks out of it (the same path-safety stance as existing project reads). — **Reversibility:** reversible — epic mode later adds tables behind the same response shape.
- **D-06:** Refresh happens when the board screen opens and when the user presses **Đọc lại**, the same pattern as the workflows list on Dự án. No polling and no file watcher. The `brain.db` pump does not see file changes anyway.
- **D-07:** Bad data never blanks the board. Skip only the broken part (bad front matter, a `depends_on` that names an unknown plan, a dependency cycle, unreadable file) and list each problem in an amber warning box **`Dữ liệu GSD có lỗi`** with the file path and a Vietnamese reason. This mirrors the `workflows.json có lỗi` box.

### Waves, critical path, cross-phase
- **D-08:** Waves are **computed from the edges**: wave = longest dependency path from a root, as in the design-ref mockup. The front-matter `wave:` number is **not** used for layout. When it disagrees with the computed wave, add a warning line under D-07, but do not move the item.
- **D-09:** Critical path = the longest chain of **unfinished** items, **unit weight** (each unfinished item counts 1, done items count 0), using the same algorithm as the mockup. Ignore `estimate.tokens`. Draw it as yellow lines only (design ref).
- **D-10:** Cross-phase edges: the roadmap's `Depends on: Phase X` links phase X's sink plans (plans nothing else in X depends on) to this phase's root plans (wave 0), so `Mọi epic` gives one connected graph with one critical path. Explicit cross-phase `depends_on` in front matter (e.g. `[05-04]`) is honoured as is. **The default view is the current phase** (from `STATE.md` `current_phase`, with a fallback to the first phase that is not done) to keep the board small. `Mọi epic` is an explicit choice.

### Interaction
- **D-11:** The done-items switch is **"Thu gọn mục đã xong"**, **on by default**. A wave where every item is done collapses to a narrow column (`Wave N · 5/5 ✓`). Done items in mixed waves become one-line chips. Edges into collapsed items stay visible so dependencies still read correctly. Turning the switch off shows full cards.
- **D-12:** Clicking an item: 2px cyan ring, its whole upstream and downstream chain lit, unrelated items dimmed (design ref). A **read-only side panel** shows the key, title, phase (epic), milestone, computed wave, status, `requirements`, the "Phụ thuộc" and "Được chờ bởi" lists (each entry clickable to move focus), and the `PLAN.md` path relative to the repo. It does not show the plan body. Keyboard: items are focusable, Enter/Space selects, Esc clears focus and closes the panel.

### Carried forward (locked in earlier phases — do not re-decide)
- Stack and design rules from 05.1 D-07: Tailwind v4 standalone build (`scripts/build-css.sh`), Alpine CSP build, no CDN, offline, Vietnamese copy, light and dark themes, 05-UI-SPEC typography and banned classes, and `scripts/dashboard-ui-lint.sh` must pass.
- Status vocabulary from 05.1 D-08 and the design ref (one set across views). The board scrolls sideways inside its own container. The page body never scrolls sideways.
- Security: `127.0.0.1` plus a startup token, with the same auth middleware and headers as every route.

## Summary

The board is a thin read-only slice. A new pure module derives items, edges, waves, statuses and the critical path from facts; a new scanner module reads `.planning/ROADMAP.md`, `.planning/STATE.md` and the front matter of `.planning/phases/*/*-PLAN.md` under strict caps; `GET /api/board` glues them in `spawn_blocking` (the existing `blocking()` helper). The screen is `screens/board.html` + `js/board.js`, registered like the other five screens. No new crate, no `brain.db` change, no new POST route.

Five facts measured on this repo change how the plan should be written. (1) The first real data source has 88 plans and 88 matching SUMMARY files, front matter of at most 11,643 bytes, and only three `depends_on` shapes (`[]`: 19, bare `[02-01, 02-02]`: 32, double-quoted `["05.2-01", "05.2-02"]`: 37). (2) There is **no cross-phase `depends_on` anywhere** (CONTEXT's `[05-04]` example does not occur), so D-10's "explicit cross-phase" branch can only be tested with fixtures. (3) Front-matter `wave:` is **1-based** and equals the intra-phase computed wave + 1 for all 88 plans; the board shows wave 0 first, so the D-08 mismatch check must compare against `computed_in_phase + 1`. (4) ROADMAP.md has **no milestone sections** and **no top-list checkbox for any decimal phase** (only Phases 1-6), so the milestone filter hides itself here and a plan-less decimal phase like 05.5 is "not done" only by absence of a `[x]`. (5) `report::front_matter` returns `None` on the first indented line, i.e. on every real plan, so it cannot be reused.

For the UI, probing the vendored Alpine 3.17.4 CSP build in headless Chrome showed what works: ternaries, `&&`, comparisons, arithmetic, object literals in `:style`, method calls with loop variables, `@keydown.escape.window`; and what does not: arrow functions, template literals, `x-html` (rendered nothing), and `<template x-for>` **inside an `<svg>`** (rendered nothing). The workable declarative design is one small `<svg>` per edge, emitted by an HTML-level `<template x-for>`, with all geometry precomputed in JS from fixed card sizes (no DOM measurement).

**Primary recommendation:** Build `board.rs` (pure `derive`, in-module rule battery like `pipeline::derive`), `board_scan.rs` (subset front-matter parser + capped, symlink-refusing reader) and `api_board.rs`; compute layout in `board.js` from fixed constants into plain data properties (not getters); render one `<svg>` per edge; port the mockup's wave and critical-path algorithms exactly but iteratively, with sorted-key tie-breaks; and use the mockup's SHOP-01..14 data as the golden fixture.

### Pattern 2: Graph derivation (spec the planner can copy)

Inputs (`board::derive(&Facts, &Filter) -> View`):
- `phases: Vec<PhaseFact { num: PhaseNum, name, milestone: Option<String>, depends_on: Vec<PhaseNum>, checkbox: Option<bool>, roadmap_plans: Vec<(id, title, checked)> }>`
- `plans: Vec<PlanFact { id, phase: PhaseNum, title, fm_wave: Option<u32>, depends_on: Vec<String>, requirements: Vec<String>, done: bool, path }>`
- `current_phase: Option<PhaseNum>`
- `PhaseNum` = `Vec<u64>` of dot components, compared **component-wise numerically**, displayed zero-padded to 2 digits on the first component (`"5"` → `05`, `"5.4"` → `05.4`, `"05.10"` stays). Never parse as `f64`: `05.1` and `05.10` collide and `05.9 < 05.10` must hold. Item order = `(PhaseNum, plan number as integer)`; placeholder = plan number 0.

Steps, in order:
1. **Items.** One per plan file (key = filename id). Duplicate key (same id in two dirs) → keep the first in order, warn. For each roadmap phase with **zero plan files**, one placeholder item, key = padded phase number (`05.5`, `04`), `done` = roadmap top-list `[x]`, else (fallback, see Assumptions A7) all `roadmap_plans` lines `[x]` and at least one. A phase dir with plans but absent from ROADMAP gets a synthesized epic from the dir name plus a warning.
2. **Explicit edges** `dep → plan`: `depends_on` entry equal to the plan's own id → warn, drop; not in the item set → warn, **drop the edge** (the item is not blocked by a ghost; Assumptions A8); duplicates collapsed. Entries are matched as strings after trimming quotes; an id that does not match `^\d+(\.\d+)*-\d+$` is also "unknown".
3. **Phase links (D-10).** For every phase `P` and every `X` in `P.depends_on` that exists: `roots(P)` = items of `P` with no incoming edge from step 2 (any phase); `sinks(X)` = items of `X` with no outgoing edge to another item of `X`. Add `s → r` (kind `phase`) for each pair not already present. A plan-less phase's placeholder is both root and sink. Cap: if `|sinks|×|roots| > 256` for one phase pair, skip that link and warn (hostile fan-out guard; this repo's max is 5×8 = 40). Unknown phase number in `Depends on` → warn, skip.
4. **Cycle break (D-07).** Iterative DFS over items in item order, dependency lists sorted by item order. A back edge (to a node currently on the stack) is dropped; warn once per dropped edge with the cycle path: `vòng phụ thuộc: A → B → A, đã bỏ cạnh B → A`. All items stay on the board. The DFS finishing order (dependencies first) is the topological order used below. Recursion is forbidden: a 2,000-plan chain would overflow the stack.
5. **Status on the full graph** (before filtering): `xong` if `done`; else `san_sang` if every remaining dep is `done`; else `bi_chan`. (A done item with unfinished deps stays `xong`.) Status uses the full graph so a dependency in another epic still blocks.
6. **Filter.** Visible set `V` = items whose epic matches `epic` (or all) AND whose epic's milestone matches `milestone` (or any). Edges kept only if both ends are in `V`. Out-of-view direct neighbours become `external` stubs `{key, title, epic, status}`; each item carries full-graph `waits_on` / `waited_by` key lists.
7. **Waves on the visible subgraph** (design ref line 509: "wave = longest dependency path from a root"): `wave(v) = 0` if no in-`V` dependency, else `max(wave(dep)) + 1`, evaluated in topological order. So `wave` can differ between the epic view and `Mọi epic`; that is correct and the panel says "computed wave".
8. **D-08 mismatch warning.** Separately compute the longest path using **only same-phase edges** (kind plan, same epic). If the plan's `fm_wave` is present and `fm_wave != that + 1`, warn `wave: ghi N, tính ra M` (M = computed + 1, because front matter is 1-based). Never move the item. On this repo this fires 0 times.
9. **Critical path on `V`**, the mockup algorithm [VERIFIED: 05.1-DESIGN-REF.html:511-514], quoted:
   ```js
   // critical path: longest chain through unfinished items (unit size per item)
   function longest(k) { var n = byKey[k]; if (n.L !== undefined) return n.L; var best = 0, nx = null; n.out.forEach(function (o) { var l = longest(o); if (l > best) { best = l; nx = o; } }); n.L = best + (n.s === "done" ? 0 : 1); n.next = nx; return n.L; }
   var start = null, bestL = -1; Object.keys(byKey).forEach(function (k) { if (byKey[k].deps.length === 0 && longest(k) > bestL) { bestL = longest(k); start = k; } });
   var crit = {}; for (var c = start; c; c = byKey[c].next) crit[c] = true;
   ```
   Port it with `outs` sorted by item order and items iterated in item order, so **ties go to the earliest item** (the mockup's JS gets this from insertion order; make it explicit). If `bestL <= 0` (nothing unfinished) there is no critical path.
   **Rendering rule (recommended, Assumptions A2):** a chain member is `critical` only if it is not `done`; an edge is `critical` only if it joins two consecutive chain members that are both `critical`. The mockup also colours chain edges that touch done members and any edge between two chain members; trimming them keeps "longest chain of unfinished items" literally true and avoids a yellow line through 50 collapsed done columns on this repo.
10. Counts for the status legend: per status, total, and number of waves.

**Golden fixture = the mockup's SHOP data** (design ref lines 490-505, statuses collapsed to done / not done). Computed this session with the mockup algorithm:
- waves: `SHOP-01:0 02:0 03:0 04:1 05:1 06:0 07:2 08:3 09:4 10:3 11:3 12:4 13:5 14:5`
- `L` values: `01:5 02:3 03:5 04:5 05:3 06:4 07:4 08:3 09:2 10:1 11:2 12:1 13:1 14:1`
- start = `SHOP-01` (first root with the max `L`=5; `SHOP-03` also has 5 and loses the tie); mockup chain `01→04→07→08→09→13`
- recommended critical nodes (done trimmed): `04, 07, 08, 09, 13`; critical edges: `04→07, 07→08, 08→09, 09→13`.
- statuses with `01`,`02` done: `03,04,05,06` = `san_sang`; the other eight = `bi_chan`.

Further rule fixtures (each its own test): cycle `A→B→A` (+ a third item untouched), self dep, unknown dep, duplicate dep, two equal-length chains (tie → smaller key), all done (no critical path), placeholder with and without checkbox, phase link with fan-out, explicit cross-phase edge suppresses a root's phase link, `05.9` vs `05.10` ordering, `epic` filter changing waves, external stubs.

### Pattern 3: Subset front-matter parser

Do **not** reuse `report::front_matter`. It is strict by design [VERIFIED: agent-brain/src/report.rs:77-86]:
```rust
if let Some((k, v)) = line.split_once(':') {
    let key = k.trim();
    if key.is_empty() || !key.chars().all(|c| c.is_ascii_lowercase() || c == '_') {
        return None;
    }
    ...
} else {
    return None;
}
```
A real plan has `files_modified:` followed by `  - .gitignore` (no colon → `None`), and `must_haves:` with `    - "INTAKE-07 (locked): the gate message …"` lines. It would return `None` for all 88 plans.

Spec for `board_scan::parse_plan_front_matter(&str) -> Result<PlanFm, FmError>`:
- strip a leading BOM; first line (after `trim_end`, which also removes `\r`) must be `---`, else `NoFrontMatter`; the closing line is the first later line equal to `---` at column 0; none within the read cap → `Unterminated`.
- Only **column-0** lines of the form `^[A-Za-z_][A-Za-z0-9_-]*:` are keys. Skip blank lines, `#` comment lines, any line starting with space/tab, and any line starting with `- ` that follows a key with an empty value (block list items). Everything else under unknown keys (`must_haves`, `estimate`, `user_setup`, `files_modified`, `type`, `autonomous`, `gap_closure`, `coupling_justified`) is ignored, including nested lines that contain `:` or `---`-looking text inside quotes.
- Recognised keys: `phase`, `plan`, `wave`, `depends_on`, `requirements`.
- Scalar: trim; drop a trailing ` #comment` outside quotes; unquote `"…"`/`'…'`.
- List: inline `[a, b]` → split on `,` outside quotes, trim, unquote; `[]` → empty; `null`/`~` → empty; empty value followed by `- item` lines at deeper indent → block list; an inline list that opens with `[` but does not close on the same line → collect continuation lines until `]` (max 20 lines) else `BadList`.
- `wave`: `u32` parse; else warn `wave không phải số nguyên` and treat as `None`.
- Duplicate keys: first wins (no warning needed).
- Bad front matter ⇒ the item **stays on the board** with `depends_on = []`, title from ROADMAP/id, and one warning (Assumptions A9): a dropped item would turn every dependent into an "unknown dependency" cascade.
- Title: ROADMAP plan line text if non-empty; else text after the first `<objective>` line: first non-blank line, cut at the first `. ` (or 120 chars), collapse whitespace, trim backticks; else the plan id. Cap 200 chars.

| Cap | Value | Basis (measured) |
|-----|-------|------------------|

| `STATE.md` | read first 16 KiB only (front matter) | front matter ~0.4 KB |
| Plan file read | first 32 KiB (`take(32768)`) | max front matter 11,643 B; objective starts within ~11.8 KB; file max 58,760 B |
| Line length for regex | 4,096 chars; longer lines skipped | regex iterators can be `O(m*n^2)` [CITED: docs.rs/regex] |
| Phase dirs scanned | 500 | 9 here |
| Plan files total | 2,000 (then stop, `truncated: true`, warning) | 88 here (~22×) |
| Items total | 2,500 | 91 here |
| `depends_on` entries per plan | 64 | max 7 here |
| `requirements` per plan | 50 | max 12 here |
| Phase-link pairs per phase | 256 | max 40 here |
| Wall-clock budget | 2 s, `Instant` checked before each file and each directory (a synchronous parse cannot be interrupted, so the check goes between files) | this repo expected well under 50 ms [ASSUMED, not benchmarked in Rust] |
| Warnings kept | 200 stored; screen shows 10 + `… và N cảnh báo khác` (same convention as `workflowErrorLines`, projects.js:354-361) | 0 here |
| Strings | title 200 chars, warning 300 chars, control characters replaced by space | |
| Query params | `project` ≤ 128, `epic` ≤ 32, `milestone` ≤ 64, `profile` ≤ 32 chars else 400 | |

Path safety rules (D-05):
1. Root = `Project::root()` (canonicalised, trusted config) [VERIFIED: agent-brain/src/projects.rs:79-82]. `Project` has `id, path, name_vi, aliases, kind, profile, repo, missing` and `kind` is the map key `"type"` [VERIFIED: projects.rs:10-19].
2. `<root>/.planning`, `.planning/phases`, each phase dir: `std::fs::symlink_metadata` must say real directory (`is_dir() && !is_symlink()`); otherwise ignore with a warning. `.planning` itself being a symlink is refused (empty state reason `planning_symlink`; Assumptions A3).
3. Each file (`ROADMAP.md`, `STATE.md`, every plan, every SUMMARY probe): `symlink_metadata` must be a regular file (`is_file()`; this also rejects FIFOs and devices that would block a read forever); open with `OpenOptionsExt::custom_flags(libc::O_NOFOLLOW)` to close the check-then-open race on the last component; read through `Read::take(cap)`.
4. A SUMMARY that is a symlink counts as absent.
5. Existing precedent for the same stance: `symlink_metadata(...).file_type().is_symlink()` skips in `fastpath.rs:198-203` and the symlink handling in `report.rs:342-366`.
6. Never put file *content* into an error status; titles and warning reasons are the only content that leaves, each length-capped and control-char-stripped. The reason this matters: a hostile repo with `ROADMAP.md -> ~/.ssh/id_rsa` would otherwise surface key lines as titles.

Concurrency: each request is independent and bounded; no cache (D-06). Reading is sync inside `blocking()`; the multi-thread runtime has 2 worker threads [VERIFIED: mod.rs:81-85] and spawn_blocking uses a separate pool, so a slow disk never blocks SSE or other routes.

### Pattern 5: API contract

`GET /api/board?project=&epic=&milestone=&profile=` (all optional). Errors use `json_error`: 400 bad/too-long param or unknown `profile` (`crate::profile::check_profile` as in api_projects.rs:84-89), 404 `Không tìm thấy dự án {id}` (api_projects.rs:397-405 wording).

- `project` absent → server picks the first project (map order, after the `profile` filter) that has `.planning/ROADMAP.md`; none → `state:"empty"`, `reason:"no_board_projects"`.
- `profile` filters only the `projects` list and the default pick; an explicit `project` is always honoured (the shell's profile selector is documented as "Chỉ lọc danh sách và thống kê", index.html:25).

### Pattern 6: Frontend (what the screen must do under Alpine CSP)

Consequences: no arrow functions or template literals in any binding; precompute strings in JS; edges are one `<svg>` per edge; put every bound value behind a method or property.

**State, not getters.** Alpine getters re-run on every access, so a getter that lays out 91 items would run once per binding per item. Compute `rebuild()` once after load / collapse toggle and store `cols`, `cards`, `edgeViews`, `canvasStyle`, `waveViews` as plain properties; selection changes only recompute a `lit` lookup object and a `selectedItem`.

**Layout model (fixed sizes, no measurement).** Constants (all multiples of 4; the design ref's 214/34/10 px are off-scale, 05.1-UI-SPEC.md:76 says "translated to the on-scale values"): `COL_W 216` (`w-54`), `RAIL_W 96` (`w-24`), `GAP_X 32`, `HEAD_H 32`, `ROW_GAP 8`, `CARD_H 64` (`h-16`), `CHIP_H 32` (`h-8`). Per wave: a **rail** if collapse is on and every item in the wave is done (header `Wave N` over `5/5 ✓`, items drawn as key-only chips so edges, selection and keyboard still work); otherwise a full column where done items (when collapse is on) are one-line chips (`CHIP_H`, key + ✓ + truncated title) and the rest are cards (`CARD_H`). Edge: from right-middle of the source to left-middle of the target; bounding box `left = x1`, `top = min(y1,y2) - 2`, `width = x2 - x1`, `height = |y2 - y1| + 4`; local path `M0 y1' C mx y1' mx y2' w y2'` with `mx = w / 2` (the mockup's cubic, design ref lines 567-569). Because every edge goes from a lower to a higher wave, `x2 > x1` always.

Layering without opacity tricks: edges `z-0`/`z-10` (crit/hot), cards `z-20` with opaque backgrounds, so edges pass behind cards ("edges are drawn under cards, never through text", design ref line 435).

### Anti-Patterns to Avoid

- **Recursive DFS for waves/critical path** (mockup style): fine for 14 items, a stack overflow for a hostile 2,000-plan chain. Use the DFS-finish topological order.
- **Reusing `report::front_matter`** or adding a YAML crate (see above).
- **Trusting `wave:`** for layout (D-08) or comparing it to a 0-based computed wave.
- **Float phase numbers**, or string-sorting `05.10` before `05.9`.
- **Getters that build the layout**; **`getBoundingClientRect` measuring**; **`x-html`**; **`<template x-for>` inside `<svg>`**.
- **Dropping an item on bad front matter** (cascades into unknown-dependency warnings).
- **Following any symlink under `.planning/`** or reading a non-regular file.
- **Serving status words from the server**: keep ASCII ids server-side and words/glyphs in `app.js` maps like `STATE_WORDS` (one vocabulary across views, 05.1 D-08).

## Common Pitfalls

### Pitfall 1: `wave:` off by one
**What goes wrong:** warnings fire on every plan, or the panel says "wave 3" for what GSD calls wave 4.
**Why:** front matter is 1-based (GSD template), the board is 0-based (design ref: "wave 0 has no dependencies").
**Avoid:** compare `fm_wave` with `intra_phase_computed + 1`; test with the real shape (all 88 agree).
**Warning sign:** warnings on a clean repo.

### Pitfall 2: Intra-phase vs displayed wave
**What goes wrong:** with D-10 links the displayed wave of a 05.2 plan is ~25, so a naive comparison with `wave: 3` warns everywhere in `Mọi epic`.
**Avoid:** the D-08 check uses only same-phase `plan` edges (step 8), independent of the view.

### Pitfall 3: Phase numbers
**What goes wrong:** ROADMAP says `Phase 5` / `Phase 2.1`-style, folders say `05-…` / `05.1-…`, plan ids say `05-13`. `05.10` sorts before `05.9` as text; `05.1` equals `05.10` as a float.
**Avoid:** `PhaseNum = Vec<u64>`, pad the first component to 2 digits for display and for matching, cap component length (6 digits) and reject overflow with a warning.

### Pitfall 4: Placeholder status for decimal phases
**What goes wrong:** only integer phases have a top-list checkbox; after `/gsd-cleanup` archives a finished decimal phase's directory (workflows/cleanup.md moves dirs to `.planning/milestones/v{X.Y}-phases/` [CITED: cleanup.md:3]), it becomes a plan-less phase with no `[x]` and would show as `sẵn sàng`.
**Avoid:** fallback (A7): phase is done if the ROADMAP lists ≥ 1 plan line for it and all are `[x]`. Test it.

### Pitfall 5: Parenthetical phase mentions in `Depends on`
**What goes wrong:** `Phase 2 (và kết quả … từ Phase 1)` yields phase 1 as a dependency too.
**Avoid:** parse only the text before the first `(`; test with the two real lines.

### Pitfall 6: Alpine CSP surprises (all probed)
**What goes wrong:** arrow functions and template literals silently render nothing; `x-html` renders nothing; `<template x-for>` inside `<svg>` renders nothing; getters recompute per access.
**Avoid:** see Pattern 6 table. Keep bindings to property reads, method calls and simple operators; return object literals from methods for `:style`.

### Pitfall 7: `dashboard-ui-lint.sh`
**What goes wrong:** the gate fails with `Thiếu FOCUS: …`.
**Why:** it matches `<(a|button|input|select|textarea)\b[^>]*>` in `index.html` and `screens/*.html` and requires a **static** `class="…"` containing `focus-visible:outline-2` [VERIFIED: scripts/dashboard-ui-lint.sh:30-31 and 45]:
```python
tag_re = re.compile(r'<(a|button|input|select|textarea)\b[^>]*>', re.DOTALL)
class_re = re.compile(r'(?<![:\w-])class="([^"]*)"')
```
`:class` does not count. `[^>]*` ends at the first `>`, so an attribute value containing `>` (e.g. `x-show="n > 1"`) truncates the tag and can hide or invent a class; keep comparisons in getters/methods. Markup built in JS strings is not linted, but the board has none.

### Pitfall 8: Banned classes, sizes and weights; text opacity
**What goes wrong:** the design ref uses 12.5px/11px type, `opacity: .62/.28` on whole cards, 7/9px paddings, 214/34/10px sizes. 05-UI-SPEC allows exactly four sizes (`text-sm/base/xl/2xl`) and weights 400/600 and bans `text-xs`, `font-medium`, `font-bold`, `p-5`, `px-2.5`, `py-0.5`, `px-3`, `py-3`, `p-3`, `gap-3`, `min-h-10`, `h-3` [VERIFIED: 05.1-UI-SPEC.md:29 and 05-UI-SPEC.md:74]. 05.1-UI-SPEC.md:124 adds: "Never lower opacity on text (`opacity-*` is not used on any element that holds text)".
**Avoid:** keys `font-mono text-sm`, status word `text-sm font-semibold`, titles `text-sm leading-normal` with `truncate` (clipped text must use `leading-normal`, 05-UI-SPEC.md:87), paddings `p-2`. Done cards use the emerald tint, not opacity. The dim state of focus mode is the one deliberate exception (design ref D-12 "dim to 28%"; `opacity-25`), transient, non-informational, reachable by keyboard, and chain members are also listed in the panel; flag it in the UI-SPEC delta. There is no automated grep for the banned list in `scripts/` (searched: no hit for `font-medium|text-xs` in scripts/ or tests/), so add a grep check to the plan's verify steps.

### Pitfall 9: Asset table and its tests
**What goes wrong:** `assets_table_matches_tree` fails (count mismatch) or the board 404s.
**Why:** assets are compiled in via `include_bytes!` and the table must list every file under `assets/dashboard` except `VENDOR.md` (dashboard_assets.rs:96-147). `asset_references_resolve` has a **hard-coded screen list** `for name in &["overview", "assign", "task", "stats", "projects"]` (dashboard_assets.rs:153) that should gain `"board"`.
**Also:** `dash09_no_external_loads` forbids `src="http`, `href="http`, `//cdn`, `url(http` … in any asset except `vendor/`; do not write `xmlns="http…"` as `href=`; inline `<svg>` in HTML needs no xmlns.

### Pitfall 10: `app.css` must be rebuilt and committed
**What goes wrong:** new utility classes do nothing in the browser (the binary embeds the committed `app.css`).
**Avoid:** last task runs `bash scripts/build-css.sh` then `bash scripts/build-css.sh --check`; commit `app.css`. Baseline passes today. `input.css` scans the whole `assets/dashboard` tree (`@source "../assets/dashboard"`), JS strings included [VERIFIED: agent-brain/dashboard-src/input.css:1-3].

### Pitfall 11: Hash routing and state
**What goes wrong:** deep link `#/board?project=x` lands on Tổng quan.
**Avoid:** exact-match router; keep selection in component state or `localStorage` (`ab.board.project`, `ab.board.collapse`). Persisting the switch is allowed, default stays on (D-11).

### Pitfall 12: Fan-out and size blow-ups
**What goes wrong:** phase links are `|sinks| × |roots|`; a 1,000 × 1,000 pair is a million edges and a hung request.
**Avoid:** the 256-pair cap, the 2,500-item and 20,000-edge caps, the 2 s deadline.

### Pitfall 13: Duplicate keys
**What goes wrong:** `x-for` with duplicate `:key` breaks rendering. Two phase dirs can hold the same plan id; two warnings can have identical text.
**Avoid:** server de-dupes item keys with a warning; warnings use the index as key.

### Pitfall 14: Test hygiene
**What goes wrong:** flaky suite. STATE.md records `contract_guard::guard_contract_cases` panicking with `BrokenPipe` occasionally (tests/contract_guard.rs:202). Run dashboard suites with `--test-threads=1`; if only that known test fails in a full run, re-run it once and note it.

### Pitfall 15: `.planning` is in git but agy must not touch it
Test fixtures create their own `.planning` inside a temp repo; never write fixtures into the real `.planning/`. The real-repo expectation is a live check, not a cargo test.

fn parse_inline_list(v: &str) -> Option<Vec<String>> {
    let inner = v.trim().strip_prefix('[')?.strip_suffix(']')?;
    if inner.trim().is_empty() { return Some(Vec::new()); }
    let mut out = Vec::new();
    for part in split_outside_quotes(inner, ',') {

        let t = t.strip_prefix('"').and_then(|s| s.strip_suffix('"'))

}

### Waves and critical path (sketch, Rust, iterative)
```rust
// items are sorted by `order`; deps/outs hold indices sorted ascending; `topo` = dependencies before dependents
fn waves(topo: &[usize], deps: &[Vec<usize>]) -> Vec<u32> {
    let mut w = vec![0u32; deps.len()];
    for &v in topo { for &d in &deps[v] { w[v] = w[v].max(w[d] + 1); } }
    w
}
fn critical_chain(topo: &[usize], deps: &[Vec<usize>], outs: &[Vec<usize>], done: &[bool]) -> Vec<usize> {
    let n = deps.len();
    let (mut l, mut next) = (vec![0u32; n], vec![None; n]);
    for &v in topo.iter().rev() {                      // dependents first
        let (mut best, mut nx) = (0u32, None);
        for &o in &outs[v] { if l[o] > best { best = l[o]; nx = Some(o); } } // strict >: earliest wins ties
        l[v] = best + if done[v] { 0 } else { 1 };
        next[v] = nx;
    }
    let (mut start, mut best_l) = (None, -1i64);
    for v in 0..n { if deps[v].is_empty() && (l[v] as i64) > best_l { best_l = l[v] as i64; start = Some(v); } }
    if best_l <= 0 { return Vec::new(); }              // nothing unfinished
    let mut chain = Vec::new(); let mut c = start;
    while let Some(v) = c { chain.push(v); c = next[v]; }
    chain                                               // caller trims done members (A2)
}
```

// Source: design ref lines 553-571, adapted to fixed sizes
var COL_W = 216, RAIL_W = 96, GAP_X = 32, HEAD_H = 32, ROW_GAP = 8, CARD_H = 64, CHIP_H = 32;
function layout(items, edges, collapse) {
  var byWave = [];                                   // items already sorted by wave, then server order
  items.forEach(function (it) { (byWave[it.wave] = byWave[it.wave] || []).push(it); });
  var x = 0, pos = {}, cols = [];
  byWave.forEach(function (list, w) {
    if (!list) return;                                // gaps cannot occur (longest path), guard anyway
    var allDone = list.every(function (it) { return it.status === 'xong'; });
    var rail = collapse && allDone, width = rail ? RAIL_W : COL_W, y = HEAD_H + ROW_GAP;
    list.forEach(function (it) {
      var chip = rail || (collapse && it.status === 'xong'), h = chip ? CHIP_H : CARD_H;
      pos[it.key] = { x: x, y: y, w: width, h: h, chip: chip, rail: rail };
      y += h + ROW_GAP;
    });
    cols.push({ wave: w, x: x, w: width, rail: rail, done: list.filter(function (i) { return i.status === 'xong'; }).length, total: list.length });
    x += width + GAP_X;
  });
  return { pos: pos, cols: cols, width: Math.max(x - GAP_X, 0) };
}

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Hostile repo with `ROADMAP.md`/plan/SUMMARY symlinked to a secret (`~/.ssh/id_rsa`) leaking lines as titles or warnings | Information disclosure | refuse symlinks (`symlink_metadata`, `O_NOFOLLOW`), only regular files, only inside `.planning/`; test with a symlink whose target holds a sentinel string and assert it never appears in the response |
| FIFO or device file named `*-PLAN.md` hangs a worker | Denial of service | `is_file()` check before open; deadline between files |
| Giant file / giant directory / giant plan count | Denial of service | size caps, entry caps, 2 s deadline, `truncated` flag |
| Quadratic phase-link fan-out | Denial of service | 256-pair cap, edge cap |
| ReDoS on ROADMAP lines | Denial of service | `regex` crate (linear time) per line with a 4,096-char line cap |
| Deep dependency chain stack overflow | Denial of service | iterative DFS / Kahn, no recursion |
| XSS through titles or warnings | Tampering | Alpine `x-text` only (textContent), never `x-html`; JSON escaping; CSP blocks inline script |
| Path traversal via `project`/`epic` params | Tampering | params are ids matched against parsed data, never joined into paths |
| Query-string abuse (very long, odd Unicode) | DoS / tampering | length caps, 400 |
