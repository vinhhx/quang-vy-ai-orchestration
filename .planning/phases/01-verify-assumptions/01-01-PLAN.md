## Plan notes (user limits override GSD defaults)

- One plan with exactly 8 tasks, one per spike, in order S1..S8. The shared setup goes into Task 1. By GSD default each checkpoint would be its own task; here checkpoints are nested `<checkpoint>` blocks inside the spike task that owns them.
- Tracer-first is satisfied by Task 1, which is typed `tracer`. It is the end-to-end slice: clean-env wrapper → run → raw capture → scrub → scan → results section → validator.
- The sizing rule ">5 files per task" is waived for Task 1 because the user folded all setup into it.
- The API-coverage, assumption-delta and schema checkpoints are skipped. This phase integrates no API, changes no identity model and touches no schema.
- Package legitimacy: nothing is installed. No audit task is needed; T-1-SC is kept in the threat model.
- At planning time the repo was not a git repository. D-03 "commit" happens through the normal executor commit flow, and the scan gate applies before any `git add`.

## Executor protocol for nested checkpoints

- `<checkpoint gate="blocking">`: stop, return `## CHECKPOINT REACHED` with the checkpoint's `<instructions>` and `<resume-signal>`, and resume at the next step of the same task once the signal arrives.
- `<checkpoint gate="non-blocking">` (SPK-10 only): show the question to the user and do NOT wait. Continue with the next task. The answer is required before the final checkpoint in Task 8.
- Each `verify.sh` checks that the evidence is complete. It never checks the spike's outcome: a Không đạt finding is a valid result. The one exception is S1's `result`/`usage` smoke check from VALIDATION.md.
