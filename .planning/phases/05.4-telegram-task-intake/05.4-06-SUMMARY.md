# Phase 05.4 Plan 06: outcome report, daily cap and command menu Summary

**The bot now follows a job started by `Tạo task` on its poll thread and reports `Đã tạo task N · branch` or the job's last error lines. Telegram-created tasks are capped per local day (`telegram_max_tasks_per_day`, default 10, counted from brain.db so a restart does not reset it). The `/task` and `/huy` command menu is registered with `setMyCommands`.**

## Accomplishments

- `intake.rs`: `Watch` entries are pushed when `start_new_task` returns `Started` (through a new `Next::Started(Watch)`, oldest dropped at `MAX_WATCH = 20`). `tick` calls `watch_tick`, which opens the DB once per pass. Each entry ends in exactly one of three ways: (1) the row exists, so `CREATED_FMT` is sent with no buttons; (2) the job is gone or exited and a second lookup still finds no row, so `FAILED_PREFIX` is sent with the last ≤ 3 non-empty output lines, each clipped to 200 chars, or `(không có thông báo lỗi)`; (3) it is older than `WATCH_MAX_MS`, so it is dropped with one terminal line. `poll_timeout_secs` returns 1 while anything is watched and `LONG_POLL_SECS` otherwise.
- `bot.rs`: `PollState.watch` and `PollState.watch_db_failed`; the getUpdates `timeout` comes from `intake::poll_timeout_secs(&state)`; the curl limit is still `POLL_MAX_SECS`.
- `config.rs`: `telegram_max_tasks_per_day` is parsed like `dashboard_port` and `autopilot.max_rounds`, with the default in code (`DEFAULT_TELEGRAM_MAX_TASKS_PER_DAY = 10`). `assets/config.default.json` is untouched.
- `intake.rs`: `local_midnight_ms`, `CAP_REACHED_FMT`, `CAP_OFF`, and `cap_refusal`, which counts `count_tasks_since(origin telegram, local midnight)` plus watched jobs without a row and refuses with the internal-error text on a DB error. It is called when a typed flow starts and again in the Confirm branch, before the dry run.
- `mod.rs`: `setMyCommands` (`task`, `huy`) is sent once right after the connected line and its result is ignored. The fake Telegram answers it with `{"ok": true, "result": true}`.
- Terminal audit lines carry the job id, task id and refusal kind, never the request text (asserted in `outcome_reported_created`).

## Deviations from Plan

### Auto-fixed / added

**1. [Rule 2 - Missing critical functionality] `PollState.watch_db_failed`**
- **Found during:** Task 1
- **Issue:** The plan says "on error keep the entries and print one terminal line". With the 1-second poll, a database that stays unopenable would print that line every second for as long as entries are watched.
- **Fix:** One extra bool field in `PollState`. The line is printed when the watcher's DB open starts failing, and the flag is reset on the next successful open. The field is not in the plan's interface list; `PollState.watch` is as specified.
- **Files modified:** agent-brain/src/telegram/bot.rs, agent-brain/src/telegram/intake.rs
- **Commit:** 06eceac

**2. [Design detail] `Next::Started(Watch)` and `press(…, &PollState, …)`**
- **Issue:** `confirm` only received the flow, which is taken out of `state` while a press is handled. It therefore could not push to `state.watch` (Task 1) or count it for the cap (Task 2).
- **Fix:** `confirm` returns `Next::Started(Watch)` and `on_callback` pushes it. `press` and `confirm` take a shared `&PollState` so `cap_refusal(ctx, state)` can run inside the Confirm branch. Behaviour is as planned.
- **Commits:** 06eceac, 19fa041

**3. [Test helper] `reach_confirm_for` / `wait_polling_again`**
- `reach_confirm_for(request)` waits for a new `Chọn dự án` message by id, so it also works for a second flow in one test.
- `wait_polling_again` waits for a long poll of the restarted serve. The existing `wait_polling` would return immediately on the first serve's records, and an update pushed before the new serve's start-up drain would be dropped.

**4. [Test addition]**
- `outcome_reported_created` also asserts that the `Đã nhận …` edit is recorded before the created message (the must-have's order), that the report has no buttons, and that no `Telegram:` line contains the request.
- `commands_registered` also asserts that `setMyCommands` comes after `getMe`.
- The config unit test also rejects `null`.

No change to the plan's texts, files list or public names.
