## Task 1 decision (checkpoint:decision, blocking-human)

The user chose **option-column**: store the Telegram origin in a new `tasks.origin` column (brain.db schema 2 -> 3), the recommended option. The orchestrator presented the decision to the user before dispatch and passed the answer in `user_response: "option-column"`. This was the user's own answer, not an auto-selection. Task 1 changes no files, so it has no commit.

Consequence recorded for later plans: once a 05.4 binary opens the live brain.db, the installed binary (commit 2e53cd5) refuses it; rollback is restoring a brain.db backup. This plan never touched the live database; plan 05.4-08's README note covers the backup step.

- Migration 3 (`ALTER TABLE tasks ADD COLUMN origin TEXT;`), `SCHEMA_VERSION = 3`; a v2 database upgrades in place with all rows kept and `origin` NULL, proven both through `db::open` and through the real binary (`status`).
- `db::ORIGIN_TELEGRAM`, `task_origin`, `mark_task_origin` (`WHERE origin IS NULL`), `count_tasks_since`; `upsert_task` and `TaskRow` untouched.
- Hidden `--origin` (value_parser `["telegram"]`) on `Commands::Run` and `Commands::Auto`; `cmd_run` refuses it for non-lead roles, `cmd_auto` refuses it without `--start`; `cmd_lead` marks the row right after `upsert_task` and before the Lead argv is built; `auto --start` forwards it before `--`; `stage_args` has no origin.
