# Phase 05.4: Code Review Report

**Reviewed:** 2026-10-23
**Depth:** standard
**Files Reviewed:** 25
**Status:** issues_found

## Summary

I reviewed the Telegram task-intake changes in `intake.rs`, `compose.rs`, `forward.rs`, `bot.rs` and `callback.rs`. I also read the shared creation path (`start_new_task`, `run_control_as`, `ActionSource`), the origin plumbing (`db.rs`, `main.rs`, `autopilot/mod.rs`, `roles/lead.rs`, `roles/mod.rs`), the config key, the docs, and the test layout.

The security-critical paths hold up under review:
- **Authorization:** `authz` runs before any other field is read.
- **Origin spoofing:** `Origin` and `ActionSource` are chosen only by server code, so an HTTP body cannot claim to be Telegram.
- **Approve guard:** the approve refusal lives in the shared `run_control_as`, not only in the hidden button.
- **Forwarded text:**
  - `<<<` and `>>>` are neutralised in every quoted field, so the closing delimiter cannot be forged.
  - Forwards are routed before command parsing, so they are never run as commands.
  - The untrusted-data rules follow the durable `tasks.origin`, so re-plans keep them.
- **Workflow gate:** every workflow must contain `gate:you`, so no workflow can skip the dashboard approval for a Telegram-origin task.
- **Callback data:** the grammar is strict and index-bounded, and no callback state lives in client-controlled data.
- **Migration:** the schema migration is additive and transactional.

I found no critical defects. There are four warnings, mostly user-visible robustness gaps. Two sit in the new code: unbounded refusal text, and outcome notices that are sent once and then lost. One is a behaviour regression against Phase 05.3: a note beginning with `/` is no longer accepted. The fourth is a silent watch drop. Six info items cover minor consistency and maintainability points.

Not re-reported, per the brief: AR-05.4-01, AR-05.4-02, full request stored in `tasks.title`, outcome message arriving after the gate message, and the capitalised instruction.

## Warnings

### WR-01: Refusal text is sent to Telegram unbounded, so a long `dirty` list makes the edit fail and leaves the flow message with live buttons

**File:** `agent-brain/src/telegram/intake.rs:949-959` (also `762-771`, `1060`, `1243`, `542-566`)
**Issue:**
- `refuse()` edits the flow message to `format!("{REFUSED_PREFIX}{reason}")` with no length bound.
- `reason` comes from `lead_preflight`. For `kind == "dirty"` it is `"Working tree có thay đổi chưa commit …:\n" + dirty.join("\n")`, a list of every changed path (`api_tasks.rs:385-389`). That list is unbounded, and a repo with many untracked files is a normal case.
- `bot::edit` has no clipping. `render::with_suffix` clips only suffix edits, and `outbox::edit` sends the text as is.
- Telegram rejects text over 4096 characters with a 400. The outbox drops permanent errors (`outbox.rs:453-461`), so the message keeps its previous text and its buttons.
- The flow has already left `state.intake`, so the user sees an unchanged confirm or workflow screen with dead buttons. The only feedback is the `answerCallbackQuery` popup, which is cut to 200 characters.
- The same path exists in `set_instruction` (the `bot::edit` of `{REFUSED_PREFIX}{reason}` at `762-771`) and in the `bot::reply(ctx, &reason)` calls that forward `reason` to the chat.

**Fix:** Clip the text in one place, before it goes to Telegram.
```rust
// intake.rs
fn refusal_text(reason: &str) -> String {
    render::clip(&format!("{REFUSED_PREFIX}{reason}"), render::MAX_TEXT)
}
// use refusal_text(reason) in refuse() and set_instruction()
```
Alternatively, clip inside `bot::edit` and `bot::reply` with `render::clip(text, render::TELEGRAM_MAX)`. That also protects every future caller.

### WR-02: Task-created and job-failed notices are sent once, directly, and then forgotten; a transient Telegram error loses them, and the audit line still claims success

**File:** `agent-brain/src/telegram/intake.rs:1354-1383`
**Issue:**
- `watch_tick` sends `Đã tạo task …` and `Không tạo được task …` with `bot::send_message`. That is a single attempt with no retry, and its `Option<i64>` result is ignored.
- The watch entry is then dropped (`continue`), and the audit line `job N đã tạo task X` is printed as if delivery succeeded.
- Phase 05.3 keeps notifications through outages with the outbox. This path bypasses it. If Telegram is unreachable at that moment, the user has been told only `Đã nhận — đang lập plan`, and never learns the task id or the failure.
- A job that is still running with no task row after `WATCH_MAX_MS` (10 minutes) is also removed with only an audit line (`1374-1380`). The user gets no message at all. Dropping it also removes it from the `cap_refusal` "starting" count, so the daily cap undercounts it until its row appears.

**Fix:**
- Keep the watch entry until the message is delivered. Only `continue` and audit when `send_message(...)` returns `Some(_)`, otherwise leave the entry in `keep`. Put a bounded retry count or deadline on it.
- Send a final "still waiting" or "stopped watching" message when the 10-minute drop happens.
```rust
if let Some(id) = task_row_id(&conn, &w) {
    if bot::send_message(ctx, &created_text(id, &w.branch), render::no_keyboard()).is_some() {
        audit(&format!("job {} đã tạo task {id}", w.job_id));
    } else {
        keep.push(w); // retry on the next tick, bounded by WATCH_MAX_MS
    }
    continue;
}
```

### WR-03: A `Trả về Lead` note or `/task` request that starts with `/` is now swallowed as an unknown command (regression against 05.3)

**File:** `agent-brain/src/telegram/bot.rs:429-435`
**Issue:**
- In 05.3, any plain text while a note prompt was open became the note, including text starting with `/` (see `handle_update` at commit `e07071f`).
- `on_message` now treats every text whose first non-space character is `/` as a command before `on_text` runs.
- A note such as `/api/users trả 500, sửa handler`, or a request typed for an awaiting `/task`, goes to `intake::on_command` and gets `HELP_TEXT`. The note prompt or the awaiting flow stays open, so the user may not understand why.
- The same applies to the instruction on a forwarded confirm screen.
- Pasting a file path as a note is common for a Lead handoff.

**Fix:** Only treat the text as a command when no text-consuming state is open, or when `parse_command` knows the name.
```rust
let consuming = state.pending.as_ref().is_some_and(|p| !p.expired(now))
    || state.intake.as_ref().is_some_and(|f| !f.expired(now)
        && (f.stage == intake::Stage::AwaitRequest
            || (f.is_forwarded() && f.stage == intake::Stage::Confirm)));
let known = matches!(intake::parse_command(text), Some((ref n, _)) if n == "task" || n == "huy");
if text.trim_start().starts_with('/') && (!consuming || known) { ... }
```
This keeps `/huy` and `/task` working while a flow or prompt is open, and lets other `/…` text through as the note or request.

### WR-04: A failed `/task` closes the open flow and the open note prompt, and send failures are silent

**File:** `agent-brain/src/telegram/intake.rs:627-690`
**Issue:**
- `start_flow` closes the open flow with `REPLACED` ("Đã huỷ — có yêu cầu mới.") in the cap-refusal branch (`630`) and the allowlist-error branch (`638`). No new request exists in either case.
- A user who is mid-selection on forwarded messages and mistypes a `/task` while the daily cap is reached loses the selection, and the old message claims a new request replaced it.
- If `send_message` fails at `685`, the old flow and any pending note prompt have already been closed (`653-656`). The new flow is dropped and the user gets nothing.

**Fix:**
- Do not close the existing flow when the refusal happens. Reply with the refusal and leave the old flow alone.
- Do the `pending.take()` and `close()` only after `send_message` has returned `Some`, or reply with `INTERNAL` when it returns `None`.

## Info

### IN-01: `parse_command` accepts a command addressed to any bot

**File:** `agent-brain/src/telegram/intake.rs:242-262`
**Issue:** `/task@otherbot x` is run as `/task`. Only the format of the `@name` suffix is checked, not that it is this bot's username. This is harmless in the paired private chat, but it is wrong in principle and is documented as "`/task@<tên bot>` dùng như `/task`".
**Fix:** Pass the bot username from `getMe` into `BotCtx` and require `bot == username` when a suffix is present.

### IN-02: Dry-run output and real run disagree on the untrusted-prompt decision

**File:** `agent-brain/src/roles/lead.rs:175` and `342`
**Issue:** The dry run uses `opts.origin` (the CLI flag). The real run uses the durable `task_origin` from the database. A dry run of a re-plan on an existing Telegram task shows the plain `lead.md` label, while the real run uses the untrusted rules. The dry run is the preview a user checks.
**Fix:** In the dry-run branch, also read `task_origin` when the task row exists, or note in the output that the prompt choice depends on the stored origin.

### IN-03: Database errors treated as "no task" in the Telegram branch guard

**File:** `agent-brain/src/dashboard/api_tasks.rs:650-653`
**Issue:** `match project_row_id(...) { Err(_) => false }` assumes any error means "project has no row yet". A real SQLite error (busy, corrupt) also yields `has_task = false`. The OD-8 guard against re-using an existing task branch is then skipped, and `upsert_task`'s `ON CONFLICT DO UPDATE` can overwrite the title of an existing task.
**Fix:** Distinguish `QueryReturnedNoRows` from other errors. For example, add a `db::project_row_id_opt` that returns `Option<i64>`, and propagate any other error with `?`.

### IN-04: Duplicated constants and an unused tuple element

**File:** `agent-brain/src/telegram/intake.rs:83-84, 88, 294-320, 609, 1047`
**Issue:**
- `INTERNAL` and `UNAVAILABLE` duplicate `INTERNAL_TEXT` and `UNAVAILABLE_TEXT` in `bot.rs`.
- `TITLE_MAX = 120` duplicates `render::TITLE_MAX`.
- `allowed_projects` returns `(Vec<Project>, Vec<String>)`, but both callers discard the second element (`(projects, _)`), and `allowed_offers` recomputes unknown ids separately with `unknown_ids`.
**Fix:** Share the constants from one module and make `allowed_projects` return only the offers.

### IN-05: Stale test name and fixed sleeps in negative assertions

**File:** `agent-brain/tests/db_migration.rs` (`fresh_db_is_v2`), `agent-brain/tests/telegram_intake.rs:1234, 1288`
**Issue:**
- `fresh_db_is_v2` now asserts schema version 3 via `SCHEMA_VERSION`, so the name is misleading.
- The intake outcome tests use `thread::sleep(3s)` to prove that nothing is sent. This slows the suite and can pass for the wrong reason on a slow machine.
**Fix:** Rename the test to `fresh_db_is_current_schema`. Replace the sleeps with a poll-count barrier (as `wait_polling_again` already does) before the negative assertion.

### IN-06: `SCHEMA_VERSION` can drift from `MIGRATIONS.len()`

**File:** `agent-brain/src/db.rs:61`
**Issue:** `SCHEMA_VERSION: i64 = 3` is a hand-kept constant, while `open` uses `MIGRATIONS.len()` for the upgrade and the "newer version" check. The two can diverge when the next migration is added. Only tests read `SCHEMA_VERSION`.
**Fix:** Define it as `pub const SCHEMA_VERSION: i64 = MIGRATIONS.len() as i64;`, or add a unit test that asserts equality.
