# Phase 05.4 Plan 01: start_new_task extraction Summary

**One blocking `start_new_task` now owns the whole Giao viec path (validation, project resolve, workflow, preflight, argv, job start) with Telegram-only `--origin telegram` and `exists` refusals, while `POST /api/tasks` is a mapper that returns byte-identical responses; INTAKE-01..12 are registered in REQUIREMENTS.md.**

- **Duration:** about 40 min (the first `cargo` build of an empty target dir dominated)
- **Completed:** 2026-10-22
- **Tasks:** 3

## Accomplishments
- `Origin`, `StartRequest`, `StartInfo`, `StartOutcome`, `start_new_task`, `new_task_args` added to `agent-brain/src/dashboard/api_tasks.rs`; `create_task` reduced to `blocking(start_new_task)` + `start_response`. `NewTask` untouched (still exactly project, request, name, workflow, `deny_unknown_fields`), so a browser cannot claim Telegram origin.
- Dry run (`dry_run: true`) runs every check through `lead_preflight` and returns `Ready(info)` without a job, a branch change or a task row.
- `Origin::Telegram`: `--origin telegram` goes in the argv immediately before `--`; a re-plan of the checked-out task branch or a branch that already has a `tasks` row is refused with kind `exists` and the two Vietnamese reasons from the plan. The Dashboard path runs neither check.
- Regression: dashboard_run, dashboard_kill, dashboard_autopilot, dashboard_pipeline, dashboard_races, telegram_outage and telegram_actions all pass with no change to any of those files.
- REQUIREMENTS.md: `### Telegram Task Intake (GSD Phase 5.4)` section, twelve Traceability rows `Phase 5.4 | Pending`, coverage 96 (42 + 54 derived), footer updated.
