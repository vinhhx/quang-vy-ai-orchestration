## Summary

Phase 5.1 is a vertical slice with one new pure Rust module (`dashboard/pipeline.rs`), one new GET route, and a rewrite of two cards of the task screen (`task.html` stepper card and "Lịch sử run" card) plus a status-vocabulary change shared with Tổng quan. No dependency, schema, or role-protocol change is needed. All data already exists in `runs`/`tasks`; the only git facts needed are the newest `<slug>: plan` commit on the task branch (already looked up in `api_tasks.rs`, duplicated twice) and an ancestry test of each Dev run's `base_commit` against it.

The central design finding (Question 1): a Dev run's `runs.base_commit` is `HEAD` at Dev start (`dev.rs:151` `let dev_base = crate::gitops::head_sha(&proj_path)?;`, passed at `dev.rs:195` as `base_commit: Some(dev_base.clone())`), and Dev refuses to start with a dirty tree, so HEAD is always at or after the plan commit. Therefore `base_commit == plan_commit` is only true for the first Dev run on a plan; a Dev run after a Lead re-run or a manual plan re-commit starts on a descendant. The correct rule is **"plan commit is an ancestor of (or equal to) the Dev run's base_commit"** (`git merge-base --is-ancestor <plan> <base>`), with the *current* plan commit being the **newest** `<slug>: plan` commit **on the task branch ref** (not `gitops::find_commit_by_subject`, which walks `HEAD` and is only valid when the branch is checked out).

The cleanest server shape (Question 2) is a pure function `pipeline::derive(&PipelineFacts) -> PipelineView` taking `&[RunRow]` plus pre-resolved git facts (plan commit, its time, which Dev run approved it), reusing `taskstate::step_state` and `taskstate::derive(...).current_step` (called with `GitFacts::default()` exactly as `list_tasks` already does) so the vocabulary is not re-implemented. The handler is thin: DB read, a few git calls inside `blocking`, then `derive`. Extract the triplicated plan-commit lookup into one helper used by `get_task`, `post_task_action` and the new handler (do **not** attempt the full WR-12 `load_task_view` refactor in this phase).

**Primary recommendation:** Build `pipeline.rs` as a pure, closure-injectable derivation (ancestry test passed as `impl Fn(&str,&str)->bool`), have the server emit state codes, exact Vietnamese result/verdict/header strings and raw numbers (`null` = unknown), and let the client only format numbers (`fmtClock`/`fmtMinutes`/`fmtUsd`, which do not exist yet) and map state codes to classes/glyphs; refetch `/pipeline` from inside `load()` so the 3 s poll, stream `end`, and every action are covered by one hook.

### Pattern 2: Cycle, round and card algorithm (all rules in one place)

Input: runs of the task with role in `lead|dev|qa` (never `inspect`), sorted `(started_at ASC, id ASC)` — the same order `get_task` uses (`api_tasks.rs:966`).

1. **Round**: `round[run] = 1 + count of earlier runs with the same role` (D-02, task-wide, not per cycle).
2. **Groups**: maximal consecutive runs of the same role; kind `lead→plan`, `dev→build`, `qa→qa`.
3. **Cycle**: starts at 1; `cycle += 1` when a Lead group begins and the previous group was `dev` or `qa` (Lead→Lead stays in the same group, so a failed Lead followed by a re-run is one plan group). A QA→Dev→QA sequence is four groups under one cycle number (UI-SPEC).
4. **Group header text** (server composes): plan group cycle 1 `Chu kỳ 1 · plan đầu tiên`, plan group cycle k≥2 `Chu kỳ {k} · plan lại`, build `Chu kỳ {k} · build`, QA `Chu kỳ {k} · QA`.
5. **Header right** (plan groups only): `bạn đã duyệt` if any Dev run exists after this group and before the next Lead run (run-order rule, as specified, independent of git); else `chờ bạn` if it is the latest plan group of the task, its last Lead run has `status=succeeded` and no Dev run follows; else `null`.
6. **Current cycle** = cycle of the last group. A role card's *state/result* come from the latest run of that role **inside the current cycle**; if the role has runs only in earlier cycles the state is `cho` ("chưa bắt đầu") but metrics still sum **all** runs of the role (A2, A12). (The latest Lead run is always in the current cycle by construction.)
7. **Card metrics**: `duration_ms` = sum of known per-run durations over all runs of the role; `cost_usd` = sum of costs that are *known* (see unknown rules); both `null` when the role has no run (renders `—`).
8. **Row unknown rules** (emit `null`, client prints `—`): `cost_usd` is `null` when `status == "killed"` or `usage_source != "result"`; `turns` is `null` when `num_turns` is `NULL`; `duration_ms` is `null` when the run has no `ended_at` and is not `running`; for `running` it is `now_ms - started_at` (server clock, `.max(0)`).
9. **Verdict per row**: `state = taskstate::step_state(Some(run)).0`; additionally `dat` when `state == "xong"` and `outcome == "qa:pass"`. Words: `dang_chay→đang chạy`, `dat→đạt`, `can_sua→cần sửa`, `vuong_mac→vướng mắc`, `vi_pham→vi phạm giao thức`, `killed→đã dừng`, `loi→lỗi`, `xong→xong`. Precedence already matches UI-SPEC (running, outcomes, killed, failed/timed_out/lost, succeeded) because it *is* `step_state`'s order `[VERIFIED: taskstate.rs:56-76]`.
10. **Total**: `runs` = number of listed rows; `duration_ms` = sum of known row durations (client rounds the *sum*); `cost_usd` = sum of known costs; `cost_unknown` = rows whose cost is `null` (drives the `Chưa tính chi phí của {k} run...` note). Running runs count in `runs` and in `cost_unknown`.
11. **Current card ring**: map `current_step` `lead→plan`, `qa→qa`, `dev→code`, except `dev` while the gate is `cho_ban` → `ban`; `null` when the task has no runs (UI-SPEC).

### Pattern 3: Gate rule ("Bạn")

- **Current plan commit** = first line of `git log --format=%H %s <task.branch>` whose subject equals `"{slug}: plan"` (newest first). This is the existing logic duplicated at `api_tasks.rs:816-832` and `1099-1115` `[VERIFIED: read]`. Do **not** use `gitops::find_commit_by_subject` (`gitops.rs:142-157`): it runs `git log ... HEAD`, which is only the task branch when the task branch is checked out; `qa.rs` can use it because QA refuses to run off-branch.
- **Plan commit time** (for `từ {time}`): `git show -s --format=%ct <sha>` × 1000 (committer time). UI-SPEC A13 proposes the end time of the latest succeeded Lead run because "plan commit time is not stored"; git does store it and it stays correct when the user re-commits the plan by hand (no Lead run). Recommend git time with fallback to the Lead run's `ended_at`. `[ASSUMED A2]` (deviation from approved A13; low risk, one field).
- **Approved** iff some Dev run `d` (any status, start order, first match) satisfies `is_ancestor(plan_sha, d.base_commit)`; gate time = `d.started_at`. `git merge-base --is-ancestor X X` is true, so the first Dev run on a freshly committed plan matches by equality. A later manual plan commit `P2` (child of `P1`) is **not** an ancestor of a Dev run that started on `P1`, so the gate correctly returns to `chờ bạn`; a Lead re-run does the same.
- `d.base_commit IS NULL` (should not occur for role-started runs; `insert_run` accepts NULL): fall back to `d.started_at >= plan_at_ms`.
- **States**: `Commit{approved_by: Some}` → `xong` / `đã duyệt plan`; `Commit{approved_by: None}` → `cho_ban` / `chờ duyệt plan`; `NoCommit` → `cho` / `chưa có plan`; `Unknown` (git/branch unreadable) → run-order fallback: latest *succeeded* Lead run exists → approved iff a Dev run started after its `ended_at`, else `cho_ban`; no succeeded Lead → `cho`.
- **Verified code path for Dev `base_commit`:** `dev.rs` requires the right branch (`dev.rs:69-79`), a clean tree (`dev.rs:81-93`), then `let dev_base = crate::gitops::head_sha(&proj_path)?;` (`dev.rs:151`) and `base_commit: Some(dev_base.clone()),` (`dev.rs:195`). Lead stores the *task base* instead (`lead.rs` `base_commit` of the branch point) and QA stores the plan commit (`qa.rs:164` `base_commit: Some(plan_commit.clone()),`), so **only Dev rows are valid for the gate test**.
- Dev that ends `dev:blocked` commits its pending change as `"{task}: vướng mắc"` (`dev.rs:288-314`), not as a plan commit, so the plan commit stays P1 until the user commits `"{slug}: plan"`; gate then reads `xong` (Dev ran on P1) until the plan is re-committed. This is correct per D-03.

### Anti-Patterns to Avoid

- **Re-implementing state mapping in pipeline.rs** (copy of `step_state`): call `taskstate::step_state` and `taskstate::derive` instead; add only `dat` and `cho_ban`.
- **Using `find_commit_by_subject` (HEAD-based) for the plan commit** on a screen that must work while another branch is checked out.
- **Testing `base_commit == plan_commit`** for approval: false for every Dev run after the first plan commit (Lead re-run, manual re-commit).
- **String-concatenated Tailwind classes** (`'bg-' + color`): invisible to the scanner; use one getter per state with literal strings.
- **Third copy of the plan-commit lookup** in `get_pipeline`: extract a helper and call it from all three handlers.
- **Making `/pipeline` failure break the action strip**: the strip must read `task.actions` only (UI-SPEC).
- **Server-side paging**: adds a contract with no benefit; total row needs all runs anyway.

## Common Pitfalls

### Pitfall 1: Gate false-negative after the first Dev run
**What goes wrong:** Gate stays `chờ bạn` (or flips wrongly) after Dev because `runs.base_commit != plan sha`.
**Why it happens:** Dev's `base_commit` is HEAD at start, which can be a descendant of the plan commit (dev.rs:151); only the very first Dev run after a plan commit equals it.
**How to avoid:** ancestry test (`is_ancestor(plan, dev.base_commit)`), `is_ancestor` returns true for equal commits.
**Warning signs:** HTTP test sequence Lead → Dev → manual `sua-app: plan` commit → relead shows gate `xong` → `cho_ban` → `cho_ban`; a unit test with a Dev `base_commit` that is a *child* of the plan sha must say approved.

### Pitfall 2: Running run shows `12 lượt` in the UI-SPEC example but the data has none
**What goes wrong:** Implementer invents turn counts for a running run.
**Why it happens:** `num_turns` is written only by `finish_run` (`db.rs:324-362`); a running row has `num_turns NULL`, `usage_source 'none'`, `cost_usd 0` `[VERIFIED: db.rs schema default + finish_run]`.
**How to avoid:** follow the per-field unknown rule: running row prints `— · {live minutes} · —` (UI-SPEC example `12 lượt · 1 phút · —` is illustrative; the rule text governs).
**Warning signs:** a number in the turns column of a `dang_chay` row.

### Pitfall 3: `0` cost shown for unknown cost
**What goes wrong:** Killed/partial runs print `$0.00` and totals look "matched" while hiding data loss.
**How to avoid:** `cost_usd: null` when `status=="killed"` or `usage_source!="result"` (fake claude writes `total_cost_usd: 0` with `usage_source result`, which is a *known* `$0.00`, so HTTP tests must seed non-zero cost with a direct `UPDATE runs SET cost_usd = ...` to make equality with `SUM(cost_usd)` meaningful).

### Pitfall 4: Static assets are compiled in
**What goes wrong:** Smoke/keys pass or fail against stale JS/HTML/CSS.
**Why:** `assets.rs` uses `include_bytes!`, `scripts/dashboard-smoke.sh` runs `agent-brain/target/debug/agent-brain`.
**How to avoid:** every UI task's verify starts with `cargo build --manifest-path agent-brain/Cargo.toml --offline --locked` (≈ seconds when warm), then the smoke command.

### Pitfall 5: `app.css` rebuilt in two plans
**What goes wrong:** merge noise/`--check` failures when two plans both regenerate the minified file.
**How to avoid:** only the **last** UI plan runs `bash scripts/build-css.sh` and commits `app.css`; earlier plans only run the lint/grep gates; final gate is `bash scripts/build-css.sh --check`.

### Pitfall 6: Lint regex needs a static `class="…focus-visible:outline-2…"`
**What goes wrong:** `scripts/dashboard-ui-lint.sh` fails on new ledger-row `<button>` or the strip buttons.
**Why:** it matches `class="..."` (not `:class`) on every `<a|button|input|select|textarea>` and requires `focus-visible:outline-2` inside it `[VERIFIED: dashboard-ui-lint.sh]`.
**How to avoid:** put the FOCUS string in the static `class`, put state styling in `:class`. Also the flow-scroll `<div role="region" tabindex="0">` is not matched by the regex but UI-SPEC still wants FOCUS on it.

### Pitfall 7: Native button activation in CDP keyboard checks
**What goes wrong:** the new "Enter on a focused ledger row" check passes vacuously or never selects the run.
**Why:** probed on this machine: `Input.dispatchKeyEvent` `keyDown`+`keyUp` **without** `text` does not click a focused `<button>`; with `text:'\r'` (Enter) or `text:' '` (Space) it does `[VERIFIED: probe in headless Chrome, output: after no-text Enter: "" / after text Enter: "C" / after text Space: "CC"]`. The existing `pressKey` helper in `scripts/dashboard-keys.mjs` sends no `text`, so the new check needs a `pressKeyText` variant (or an optional `text` param).

### Pitfall 8: Seeded rows must not become the "latest run"
**What goes wrong:** seeding 25 extra runs for the paging check makes the screen open an SSE stream on a seeded run with no events, breaking the existing raw-dialog check (`#ab-log button`).
**How to avoid:** seed with small `started_at` values (older than the real Lead run) so the real run remains the newest/default; keep `tasks.status` untouched (`planned`) so `Chạy lại Lead` stays enabled for the confirm-dialog check. Alternating roles in the seed also exercises cycle headers.

### Pitfall 9: SSE `status` events fire on token changes
**What goes wrong:** refetching `/pipeline` on every `status` event during a long run.
**Why:** `StatusSnapshot` includes token counters (`sse.rs:79-100`) and an initial `status` event is always sent on connect.
**How to avoid:** refetch only when `status` or `outcome` differs from `this.streamRun`'s previous value; `end` always refetches (existing handler calls `load()`).

### Pitfall 10: Out-of-order poll responses
**What goes wrong:** a slow `/pipeline` response overwrites a newer one; or a refetch after an action races the 3 s poll.
**How to avoid:** `_pipeSeq` counter captured per request, ignore stale responses (the WR-10 identity pattern), and an in-flight guard that still allows one trailing refetch. While a request is in flight keep the previous data on screen (UI-SPEC).

### Pitfall 11: Ledger paging vs cycle headers
**What goes wrong:** windowing the *rows* leaves empty headers, or windows by groups and shows wrong counts.
**How to avoid:** window over the flat run sequence (`visibleCount` starts 20, `+= 20`); build visible groups by keeping only rows inside the window and **dropping groups with zero visible rows**; the button label/visibility depends on `totalRuns > visibleCount`; total row always uses `ledger.total` from the server.

### Pitfall 12: Lead run succeeded but plan not committed
**What goes wrong:** Lead `status=succeeded` yet plan validation failed (`lead.rs` returns `Kế hoạch trong .plan.md không hợp lệ` before the commit), so the card says `plan đã commit` (UI-SPEC copy for `xong`) while the gate says `chưa có plan`.
**How to avoid:** accepted by the spec; see Open Question 1 for the optional tweak. Test the combination so behavior is at least deterministic.

### Pitfall 13: `tasks.created_at` / `updated_at` semantics
`upsert_task` keeps `created_at` on conflict (`db.rs:174-182`), so `Bắt đầu` time is stable across re-leads `[VERIFIED: db.rs:170-186]`.

```rust
// Source: pattern of existing gitops::git (agent-brain/src/gitops.rs:5-32)
pub fn is_ancestor(root: &Path, ancestor: &str, descendant: &str) -> bool {
    let hex = |s: &str| !s.is_empty() && s.len() <= 64 && s.chars().all(|c| c.is_ascii_hexdigit());
    if !hex(ancestor) || !hex(descendant) {
        return false; // never pass DB-provided text to git as an option
    }
    git(root, &["merge-base", "--is-ancestor", ancestor, descendant]).is_ok()
}
pub fn commit_time_ms(root: &Path, sha: &str) -> Option<i64> {
    let out = git(root, &["show", "-s", "--format=%ct", sha]).ok()?;
    out.trim().parse::<i64>().ok().map(|s| s * 1000)
}
```
(`git()` maps every non-zero exit, including exit 1 "not an ancestor", to `Err`, so `.is_ok()` is the boolean; an unknown commit also yields `false`, the conservative result.)

```rust
async fn get_pipeline(State(st): State<Arc<AppState>>, AxumPath(id): AxumPath<i64>) -> Response {
    let res = blocking(move || {
        let conn = crate::db::open(&st.db_path)?;
        let task = match crate::db::get_task(&conn, id)? {
            Some(t) => t,
            None => return Ok(json_error(StatusCode::NOT_FOUND, &format!("Không tìm thấy task {id}"))),
        };
        let runs = crate::db::runs_for_task(&conn, id)?;
        let plan = plan_facts(&conn, &st, &task, &runs); // best effort, returns PlanFacts::Unknown on any git/project failure
        let latest = |role: &str| runs.iter().filter(|r| r.role == role).max_by_key(|r| (r.started_at, r.id));
        let facts = TaskFacts { task: &task, lead: latest("lead"), dev: latest("dev"), qa: latest("qa"),
                                git: &GitFacts::default(), busy: None, now_ms: crate::db::now_ms() };
        let current_step = taskstate::derive(&facts).current_step;
        let view = pipeline::derive(&pipeline::PipelineFacts { task: &task, runs: &runs, plan,
                                    current_step: &current_step, now_ms: crate::db::now_ms() });
        Ok((StatusCode::OK, [(axum::http::header::CONTENT_TYPE, "application/json; charset=utf-8")], Json(view)).into_response())
    }).await;
    match res { Ok(r) => r, Err(e) => json_error(StatusCode::INTERNAL_SERVER_ERROR, &e.message) }
}
```
