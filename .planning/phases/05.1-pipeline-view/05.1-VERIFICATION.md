### Open Code-Review Findings: Do They Defeat A Must-Have?

The ledger `05.1-REVIEW-DISPOSITION.md` shows all 11 findings as `open`. I read the cited code for each warning. None is a blocker.

**WR-03 (Lead `succeeded` with outcome `protocol_violation` still yields `chờ bạn`). Non-blocking follow-up. It does not defeat PIPE-03.**

- The review is right about the code. R9 tests only `last_run.status == "succeeded"` (`pipeline.rs:287-288`). The Unknown-path Bạn card filters on `r.status == "succeeded"` (`pipeline.rs:421-424`, `440-443`). `step_state` returns `vi_pham` for the same run, because the outcome check comes first (`taskstate.rs:66-68`). So the plan group header can say `chờ bạn` next to a row that says `vi phạm giao thức`.
- The production Bạn card does not take that path. Lead returns `EXIT_PROTOCOL` before `commit_paths` (`roles/lead.rs:207-222`), so a violating Lead makes no plan commit. With git readable, `plan_facts` returns `NoCommit` and the card reads `chưa có plan` (`pipeline.rs:430-435`). If an older plan commit exists, the card reports that commit's real gate, which matches PIPE-03 ("plan đã commit và chưa có Dev trên plan đó").
- So the wrong `chờ duyệt plan` card needs two conditions together. Git facts must be unreadable (`PlanFacts::Unknown`), and the latest successful-status Lead run must have violated protocol. The Unknown path is explicitly a degraded fallback.
- The remaining contradiction is the ledger group's right-hand text. UI-SPEC line 261 words it as "its last Lead run succeeded", and the code follows that wording on the raw status. The task banner is not affected (`taskstate.rs:329` treats the violation as attention).
- Fix: use `step_state(Some(r)).0 == "xong"` in both places, as the review suggests.

**WR-02 (`is_ancestor` maps any git error to "not an ancestor"; the gate can flip for one poll). Non-blocking follow-up. It does not defeat the PIPE-03 fallback truth.**

- Confirmed at `gitops.rs:113-119` (`git(...).is_ok()`) and `pipeline.rs:622`. An exit-128 error returns `None` from `approving_dev_run`, which becomes `Commit { approved_by: None }`, so the gate shows `chờ bạn`.
- The fallback truth is met for every failure path the plan enumerates. A missing project, an unreadable map, a missing branch and a failing `git log` all return `PlanFacts::Unknown`, and tests cover the Unknown path (`pipe03_unknown_git_*`).
- The uncovered path is narrow. The same `git log` that found the plan commit just succeeded, so a failure in the next `merge-base` needs a missing object or a spawn failure in that window. Merely rewritten history does not trigger it, because both objects stay readable and the answer is a stable `false`.
- Impact is one flipped poll, not a persistently wrong gate. This is a hardening item. Fix it before the next phase builds on the gate, using the tri-state in REVIEW WR-02.

**WR-01 (`find_plan_commit` scans full history, unbounded). Non-blocking.** It reproduces the pre-Phase-5.1 lookup at `3c2b1f5:api_tasks.rs:817-820`, now shared by three call sites as planned. The slug-reuse edge case is pre-existing behaviour. Defer to a hardening plan.

**WR-04 (`_pipeBusy` can stick on a hung request; the seq guard is dead code). Non-blocking.** There are no overlapping requests, so no stale data can arrive. A hang would freeze the pipeline silently until navigation. The behaviour is untested, but it is not required by any success criterion.

**WR-05 (escaped `\$` in a layout failure message). Non-blocking.** It affects diagnostics only when Check E already fails. It does not change pass/fail.

IN-01 to IN-06 are info items (duplicated rules, clippy, partial role-card cost sum, test gaps, duplicated `current_step`, stale `streamRun`). None breaks a truth. IN-03 matters to the human reviewer: a role card with a killed run and a normal run shows only the known run's cost, with no signal. The plan flagged unknown-as-`—` at the total level, and the card sum "over runs with a known value" follows that. Record it for UAT.

Recommendation: no gap-closure plan is needed to proceed. Triage WR-01 to WR-05 (set each to `fixed` or `deferred` in the disposition ledger) before `/gsd-ship`. WR-02 and WR-03 are the highest priority.
