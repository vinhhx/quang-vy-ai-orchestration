Summary

The two images are two different layers of the product, and they need very different amounts of work.

  • View 1, the pipeline, is mostly a presentation change. Each row in that ledger is one agent run, and brain.db already stores every run's role, outcome, turns, start and end time, and cost. Lead, Dev and QA reruns are already "rounds". What is missing is the extra stages (plan review, code review, fix, draft PR), the loop driver that runs them without a button press, and the structured verdicts ("1 blocking · 4 advisory").
  • View 2, the board, is a new layer above tasks. Today one request becomes one task on one branch. The board needs work items that depend on each other, grouped by epic and milestone. Waves and the critical path are then computed from those dependencies. Nothing in the current schema holds this.

The recommended order is: ship the pipeline view on today's data first, then add the autopilot loops, then the board. Each step is usable on its own, and all three keep the current rules: 127.0.0.1 plus token, kill only through runner::cmd_kill, one run per project, one personal run at a time.

View 1 · Task pipeline

This replaces the stepper on #/task/N. Each stage is a card with its state, a one-line result, and time and cost. Stages that loop (plan with plan review, code with code review, QA with fix) sit in a group whose footer shows the round against its cap. The Bạn card is the approval gate: autopilot never runs past it without you. The ledger underneath lists every run in order, grouped by cycle, and ends with the task total.

View 2 · Work board

A new screen, #/board. Items are laid out in waves: wave 0 has no dependencies, and each later wave depends only on earlier ones. Lines show dependencies; the yellow line is the critical path, the longest chain that decides when the epic can finish. Click an item to light up everything it waits on and everything waiting on it. The mockup below is live: try clicking SHOP-07, or use the done-items switch.

System changes

1. Protocol: five stages instead of three

StageRole runMay writeVerdict and counts
Planlead (exists).plan.md—
Plan review newplan-review.plan-review.md onlyapprove / revise; blocking, advisory
Yougate (no run)—approved at, by click or agent-brain approve TASK
Implementdev (exists)files in the plan's Thay đổi tabledone / blocked
Code review newcode-review.code-review.md onlypass / revise; blocking, advisory
Local QAqa (exists).qa-report.md (+ test files if allowed)pass / retry; specs, not automatable, failing

Draft PR opt-inno agent; git + ghremote branchPR number

Each report starts with a small front-matter block (verdict:, blocking:, advisory:, …) so the runner can parse counts without reading prose. The guard hook already enforces "may write" lists; the new roles reuse it with one-file allowlists.

2. Autopilot driver

  • A new command, agent-brain auto TASK, runs the stage machine: plan → plan review → (revise: replan) … until approve or the cap. It then stops at the Bạn gate. After you approve, it runs implement → code review → QA → fix in the same way, then the PR step if enabled.
  • The dashboard starts it like any other job (child process with PDEATHSIG, one per project). Kill on any card stops the driver and its current run through runner::cmd_kill.
  • Stop conditions: round cap reached (default 3 per loop), task budget reached (minutes or $), a blocking verdict the loop cannot clear, a protocol violation (exit 3), or Dev "Vướng mắc". Each one leaves the task in chờ bạn with the reason on the card.
  • Manual mode stays: every stage can still be started by its own button or CLI command. Autopilot is per task, off by default until you trust it.

3. Data model (SQLite migration v2)

ChangePurpose

The SSE pump (PRAGMA data_version) needs no change: any write to these tables already wakes the screens.

4. Where board items come from

  1. Epic mode for Lead (main path): agent-brain run lead PROJECT "…" --epic writes .epic.md with items, milestones and dependencies instead of one plan. You review it like a plan; approving it creates the items. Each item is then run as a normal task.
  2. Import (cheap first step): read an existing breakdown, for example this repo's own GSD ROADMAP.md and plan front matter (wave, depends_on), to get real data on the board before epic mode exists.
  3. Manual: add or edit items and dependencies on the board screen.

5. API additions

GET /api/tasks/{id}/pipelineStage cards, loop groups with round/cap, ledger rows, totals.
POST /api/tasks/{id}/approve, /auto, /auto/stopGate and autopilot control. Same Origin, Content-Type and busy-rule checks as today's actions.
GET /api/board?epic=&milestone=&profile=Items with derived status, wave, and critical flag; edges.
POST /api/items, PUT /api/items/{id}, POST /api/items/{id}/startEdit items and dependencies; start an item as a task.

Design system

Both views extend the existing dashboard contract in 05-UI-SPEC.md rather than replacing it. Same stack (Tailwind v4 build, Alpine CSP, no CDN, offline), same slate neutrals and indigo accent, same light and dark themes, same Vietnamese copy. The changes are a fuller status vocabulary, three new components, and a denser board layout.

Status vocabulary (one set for both views)

Every status has a color, a glyph and a word, so it never depends on color alone. Colors map to existing Tailwind families; dark values are the 400 shades on slate-900.

Layout and density

  • Task screen order: pipeline, ledger, then the existing plan / QA report / live log panes.
  • The pipeline scrolls sideways inside its own box below 1024px; under 640px it stacks vertically (as the stepper does today, with no arrows).
  • The board keeps the 05-UI-SPEC minimum text size (14px titles, 12.5px mono keys) and 48px touch targets for toolbar controls; cards themselves are dense, 2 lines.
  • The board defaults to dark-friendly contrast in both themes: edges are drawn under cards, never through text.

Workflow templates

A workflow is a named list of stages, which ones loop, where the gates are, and the limits. Templates live in ~/.config/agent-brain/workflows.json. Giao việc gets a Quy trình picker next to the project; the CLI takes --workflow NAME. No choice means mac-dinh. The pipeline view draws whatever stages the task's workflow lists, so a short workflow shows fewer cards.

{
  "mac-dinh": {
    "stages": ["plan", "plan-review", "gate:you", "implement", "code-review", "qa", "fix"],
    "loops":  { "plan": "plan-review", "implement": "code-review", "qa": "fix" },
    "max_rounds": 3, "budget_minutes": 60, "budget_usd": 20, "auto": true
  },
  "nhanh":     { "stages": ["plan", "gate:you", "implement", "qa"], "auto": false },
  "chi-review":{ "stages": ["code-review"], "auto": true, "budget_usd": 5 }
}
  • The task stores the workflow it started with (a copy), so editing a template never changes a running task.
  • Rules that no workflow can turn off: kill only through runner::cmd_kill, one run per project, one personal run at a time, the guard hook's write lists.
  • auto: false keeps today's behaviour: every stage waits for your button.
  • Workflows are a Phase B feature. Phase A draws today's fixed Lead → Dev → QA as the default workflow.
