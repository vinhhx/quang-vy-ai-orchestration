### Locked Decisions

#### Carried forward (locked 2026-10-19, not re-asked)
- **D-01:** Workflows are named templates in `~/.config/agent-brain/workflows.json`, picked per task (CLI `--workflow NAME`, dashboard "Quy trình"). With no choice, the default is `mac-dinh`. The task stores a **snapshot** of its workflow at start, so editing a template never changes a running task. — **Reversibility:** costly — `tasks.workflow_json` becomes part of the schema and the dashboard contract.
- **D-02:** Default limits are 3 rounds per loop, and 60 minutes or $20 per task, whichever comes first. They live in `config.json` as global defaults (D-21).
- **D-03:** Autopilot **always stops at the plan approval gate**. No workflow can skip it.
- **D-04:** Safety rules no workflow can turn off:
  - Kill only through `runner::cmd_kill`;
  - one run per project;
  - one `personal` run at a time;
  - the guard hook's per-role write lists;
  - no `--dangerously-skip-permissions` for agent runs (`check_forbidden_args`).
- **D-05:** The status vocabulary and design system of 05.1 carry over (05.1-UI-SPEC.md); running is blue and indigo is reserved for actions. `PR nháp` stays `chưa tự động`.

#### Review rules
- **D-06:** A review's verdict is `revise` **only when it has at least one blocking finding**. Advisory-only gives `approve` (plan review) or `pass` (code review). The report front matter carries `verdict`, `blocking` and `advisory` counts.
- **D-07:** Both reviews default to **opus**, configurable as `models.plan-review` / `models.code-review` in config.json.
- **D-08:** Reviewers may **read the whole repo** (read-only). Each writes **only** its own report file (`.plan-review.md` / `.code-review.md`), and the guard allowlist enforces this.
- **D-09:** On `revise`, the author re-runs **with the review report as input** and must address every blocking finding: Lead gets `.plan-review.md`, Dev (fix mode) gets `.code-review.md`. The review then runs again on the new version. Each re-run is one round.

#### QA and fix loop
- **D-10:** QA keeps today's behaviour. It reads the diff, may run the project's existing checks it finds, and writes `.qa-report.md` with `Đạt` / `Cần sửa`. It adds structured counts to the report front matter (`specs`, `failing`; `not_automatable` optional). Writing and running new test specs is deferred.
- **D-11:** The single fixer for both loops is **Dev in fix mode** (`stage = fix`). It takes the code-review or QA report as input, and the same review or QA re-runs afterwards.
- **D-12:** Fix mode may write the plan's Thay đổi files **plus files explicitly named in the input report**. Anything else is a protocol violation (guard). — **Reversibility:** reversible.
- **D-13:** If QA still fails after the round cap, autopilot stops with the task at `chờ bạn` and the last QA report. The user chooses from the stop-banner buttons (D-24).

#### Autopilot control
- **D-14:** The workflow decides the start:
  - `auto: true` workflows (`mac-dinh`) start autopilot right after Giao việc;
  - `auto: false` workflows (`nhanh`) stay manual.
  - The task screen also has `Bật autopilot` / `Dừng autopilot`, and the CLI has `agent-brain auto TASK`.
- **D-15:** `Duyệt plan` (dashboard) or `agent-brain approve TASK` (CLI) records `tasks.approved_at`. Autopilot then **continues automatically** through Code → Review code → QA → Sửa. — **Reversibility:** costly — this replaces 5.1's derived gate (D-03 of 05.1) with an explicit record; derivation stays the fallback for tasks created before 5.2.
- **D-16:** If `serve` stops while a dashboard-started autopilot runs, the autopilot and its current run stop (the Phase 5 PDEATHSIG rule). The task shows `đã dừng` and can be resumed later. An autopilot started with `agent-brain auto` in a terminal keeps running there.
- **D-17:** `Trả về Lead` at the gate takes an **optional short note**. The note is passed to Lead as extra input for the re-plan and stored with that run.

#### Budget and stops
- **D-18:** On a budget hit (60 min or $20) **mid-run**, the current run finishes, autopilot starts no further stage, and the task shows `chờ bạn · hết ngân sách`. Each role's `timeout_seconds` stays the hard ceiling.
- **D-19:** The budget counts the **equivalent API cost of all runs in the task** (the dashboard and `stats` figure). Runs with unknown cost (killed or partial) are **estimated from their partial token sums**, so the cap still holds. Minutes are the summed run durations.
- **D-20:** Stop notification is the dashboard card or banner with the reason (`hết vòng`, `hết ngân sách`, `vi phạm giao thức`, `vướng mắc`, `dừng bởi bạn`), plus one line in the `serve` or `agent-brain auto` terminal. No desktop notification.
- **D-21:** `workflows.json` may override `max_rounds`, `budget_minutes` and `budget_usd` **per workflow**. `config.json` holds the global defaults (3 / 60 / 20).

#### Built-in workflows, editing, picker
- **D-22:** Two workflows are built into the binary:
  - `mac-dinh`: plan ⇄ review plan → gate → code ⇄ review code → QA ⇄ sửa, with `auto: true`;

- **D-23:** Workflows are edited **in the file only**. The dashboard shows the workflow list read-only (stages and limits). An invalid `workflows.json` produces a Vietnamese error naming the problem and the line or key, and the built-ins keep working. No dashboard editor in 5.2.

## Summary

Phase 5.2 adds nine moving parts on top of a codebase that is in good shape (full `cargo test` passes in 26 s warm, `dashboard-js-check` 242 checks, `dashboard-ui-lint` 40 elements, `build-css --check` clean `[VERIFIED: ran all four this session]`): a schema v2, a `workflows.json` loader, two review roles, Dev fix mode, QA/review report front matter, an autopilot driver, a budget/pricing module, dashboard endpoints, and a data-driven task screen. No new crate is needed. Every piece reuses an existing seam (`execute_role`, `write_hook_settings`, `JobManager`, `pipeline::derive`, `cmd_kill`).

Eleven findings change how the phase must be planned; each has a verified source:

1. **A naive table rebuild for the role CHECK silently deletes all `events` rows.** SQLite cannot alter a CHECK, so `runs` must be rebuilt, but `db::open` sets `foreign_keys=ON` before migrating, and `DROP TABLE runs` then cascades into `events`. Reproduced on a copy of the real DB: events 252 -> 0 with FK on, 252 -> 252 with FK off before `BEGIN`. The migration runner must be restructured (Code Example 1).
2. **No pricing table exists in the repo.** D-19 says "via stats pricing", but `stats.rs` only sums `runs.cost_usd` as reported by claude, and killed/partial runs store `cost_usd = 0`. A small price module is new work. Its formula was fitted to 10 real runs and matches exactly for Opus 5.5 and Sonnet 5.5 (§3.8).
3. **The fake claude can only play one scenario for every invocation** (`FAKE_CLAUDE_SCENARIO` is one file). Autopilot loops need a per-role queue; `tests/fakes/fake_claude.py` must be extended (backward compatible with the legacy Python tests that share it).
4. **An in-process driver would become un-killable between runs.** After the first `supervise`, tokio keeps its SIGINT/SIGTERM/SIGHUP handler for the whole process and never restores the default (`tokio-1.53.3/src/signal/unix.rs:334-345`). Recommended design: the driver is a light process that spawns `agent-brain run ...` children (§3.7).
5. **`taskstate::derive` only recognises lead/dev/qa as running roles** (`taskstate.rs:291-299`), so a running `plan-review` / `code-review` run would show no Kill action and group `waiting`. It must see any running run of the task.
6. **Review reports are committed after the plan commit, so every "code changed since the plan" check must exclude them**: `qa.rs:83-84`, `api_tasks.rs:886-887` and `1216-1217`, `stream.rs:6` (`PROTOCOL_FILES`), `planfile.rs:481-486`. Missing one makes `Chạy QA` enable itself after a plan review alone.
7. **Lead's re-run overwrites `.plan.md` with an empty skeleton** (`lead.rs:153-155`), so a review-fed re-plan cannot see the previous plan unless it reads it from git or the skeleton step is skipped.
8. **`NewRun` has about 17 literal constructions in tests; `Project` about 15.** Do not add fields to either. Record stage/round/metrics with a follow-up `UPDATE`, and read the per-project `workflow` straight from the `projects_map.json` `Value` (which already preserves unknown keys and order via `preserve_order`).
9. **A live autopilot driver must count as "busy" for its project and profile, including CLI-started drivers** that the dashboard `JobManager` knows nothing about; otherwise another task can slip in between two stages of a personal-profile autopilot and fail the next stage with the E-06 error.
10. **The spec's five stop reasons do not cover a run that fails, times out, or cannot start** (dirty tree, malformed report). Recommend a sixth reason (Open Question O1, needs a UI-SPEC amendment).
11. **Sticking to the "stateless `decide()` over persisted facts" pattern makes resume, `Chạy thêm 1 vòng`, crash recovery and every stop reason unit-testable without a process** (§3.7). This is the main design recommendation.

**Primary recommendation:** Build the phase bottom-up in about 14 plans over 10 waves (full table at the end): schema v2 + config + pricing first, then `workflows.rs` and report parsing as pure modules, review roles, fix mode / Lead input / QA counts with the fake-claude queue, the driver with `auto` / `approve` / kill extension, pure dashboard derivation, endpoints, UI, smoke and docs, and last the live checks; keep each wave's plans file-disjoint with the stub-module trick in §3.2.

### 3.3 Schema v2 (AUTO-03)

**Current state.** `MIGRATIONS` has one entry; `open()` applies `MIGRATIONS.iter().enumerate().skip(current_version)` inside a transaction per entry and sets `user_version = i + 1` (`db.rs:98-106`). The live DB at `~/.local/share/agent-brain/brain.db` has `user_version = 1`, 178 projects, 10 tasks, 17 runs, 252 events `[VERIFIED: python sqlite3 on a copy]`. Two existing tests assert version 1: `tests/lib_foundation.rs:465` `assert_eq!(user_ver, 1);` and the re-open assertion near line 504; both must become 2.

### 3.5 Report format and parser (AUTO-01, AUTO-02)

New pure module `report.rs`, no YAML dependency. A report starts with a front matter block at the very top (before the `# ...` title and the `<!-- brain-meta -->` line); `planfile::section_text` ignores it because `---` lines are not headings.

```

verdict: revise
blocking: 1
advisory: 4

## Mục chặn (blocking)

**Named files (fix mode, D-12).** `report::named_files(report_text, root) -> Vec<String>`:
1. Union of (a) front-matter `files` and (b) backticked tokens in the body that look like repo-relative paths (contain `/` or a known extension, optional `:line` suffix stripped).
2. Normalise with `planfile::normalize_plan_path` (`planfile.rs:218-234`) and validate with the same rules as `validate_plan`'s path checks (`planfile.rs:464-502`: absolute, `~`, `..`, `.git`, protocol files, glob characters, `outside_root` via `realpath_nonstrict`). ### 3.7 Autopilot driver (AUTO-05)

**Process model (recommended).** `agent-brain auto TASK` is a small supervisor in its own process; for each stage it spawns `agent-brain run <role> ... --round N [...] -- PROJECT [REQUEST]` as a child **with stdio inherited**, same `pre_exec` PDEATHSIG(SIGTERM) pattern as `jobs.rs:76-99`, on the main thread (PDEATHSIG is tied to the creating thread, which is why `jobs.rs` uses a long-lived spawner thread). Children stay in the driver's process group so a terminal Ctrl+C reaches both; claude itself is in its own group (`runner.rs:214`) and is killed by the child's `supervise`.
- Signals: install `libc::sigaction` handlers for SIGINT/SIGTERM/SIGHUP that set a static `AtomicBool`; the driver main loop polls `Child::try_wait` every 200 ms, checks the flag and the DB stop flags, forwards SIGINT to the child on signal, waits for it, records `auto_state='interrupted'` (no reason banner, UI "đã dừng" for D-16) and exits 130.
- Why not in-process: see finding 4; the driver would be blind to signals between runs.
- Exit codes of children (`error.rs:1-6`): `EXIT_OK=0, EXIT_ERROR=1, EXIT_ROUTING=2, EXIT_PROTOCOL=3, EXIT_BLOCKED=4, EXIT_INTERRUPTED=130`; the driver reads the **DB** (latest run row > last seen id: `status`, `outcome`, `metrics_json`) as the authority and uses the exit code only when no run row was created (precondition failure).

**Claim and liveness.** On start: `BEGIN IMMEDIATE`; refuse if the task has `auto_state IN ('running','stopping')` with a live `(auto_pid, auto_pid_start)` (`procs::alive`); also refuse if another live driver or running run occupies the same project, or the same profile when `personal` (E-06); set `auto_state='running'`, pid, `procs::proc_id(getpid)` start time; clear stop flags; commit. Stale `running` rows with a dead pid are reclaimable. Add the same live-driver check to `busy_reason` and `busy_reason_for_task` (`api_tasks.rs:132-203, 205-303`), which today look only at running runs and `JobManager` reservations; without it a CLI-started driver is invisible between stages.

**Pure decision function** `autopilot::decide(&Snapshot, &Facts) -> Decision` (no I/O; `Facts` = ordered stage/round/outcome/status of the task's runs, `plan_committed`, `approved` (record matches current plan commit), stop flag, budget usage (§3.8), grants, `resumed: bool`). Rules, in order:
1. Stop flag set -> `Stop(dung_boi_ban)`.
2. Budget: `used_minutes >= budget_minutes || used_usd >= budget_usd` and no bypass left -> `Stop(het_ngan_sach)`; checked **before starting a stage only** (D-18: the current run always finishes; `timeout_seconds` remains the hard ceiling).
3. Plan phase (workflow has `plan`): no committed plan -> `Run(plan, r=1)`. Last loop run is Lead success and a reviewer exists -> `Run(plan_review, r)`. Last is reviewer `approve` -> phase done; `revise` -> if `r >= max_rounds + grant` then `Stop(het_vong, loop=plan, N=r, cap)` else `Run(plan, r+1, review=true)`. Reviewer-less workflow: Lead success -> phase done.
4. Gate: workflow has `plan` and not `approved` -> exit with `auto_state='gate'` (driver ends; the process is not kept alive for hours). Approval (`approve` command or API) records `approved_at`, then starts a new driver (D-15).
5. Build phase: `implement` -> `Run(code, r=1)`; with `code-review`: after Dev (impl or fix) success -> `Run(code_review, r)`; `pass` -> done; `revise` -> cap check, then `Run(fix[code_review], r+1)`.
6. QA phase: `Run(qa, r=1)`; `qa:pass` -> `Done` (`auto_state='done'`); `qa:fix` -> with a `fix` stage: if `r >= cap + grant` `Stop(het_vong, loop=qa)` else `Run(fix[qa], r)` then `Run(qa, r+1)`; without `fix`: `Stop(het_vong, N=1, cap=1)` (reviewer/QA without an author stage cannot loop; O4).
7. Last run `dev:blocked` -> `Stop(vuong_mac)`; `protocol_violation` -> `Stop(vi_pham_giao_thuc, run_id)`; run `killed` with `kill_requested_at` -> `Stop(dung_boi_ban)`; `failed` / `timed_out` / `lost` or a child that exits non-zero without creating a run -> `Stop(run_loi)` (O1). On an explicit resume (`resumed = true`) a stopped stage is retried as `Run(stage, r+1)`.
- Round semantics: author runs define the round (Lead run N, Dev impl/fix run N); a reviewer run carries the round of the author it reviews; in the QA loop the QA run defines the round and the fix after it belongs to the same round. Cap counts rounds, so with cap 3 the plan loop runs at most 3 Lead runs and ends `hết vòng` when review 3 still says `revise`.
- `Chạy thêm 1 vòng` = increment `grants[loop]` in `auto_json`, clear the stop, start the driver. For `hết ngân sách` it sets a one-shot `budget_bypass_stages: 2` (one round = author + checker, same in all three loops; O5).
- Soft stop (`Dừng autopilot`): set `auto_stop_at` / `auto_stop_kind='soft'`; the driver sees it only between stages (the run in flight finishes; UI helper text "Run hiện tại chạy nốt rồi autopilot dừng"). Kill: see §3.9.

**Stage -> child argv** (positionals after `--`, as `api_tasks.rs:562-569` does):

| Stage | argv |
|-------|------|
| plan | `run lead --name SLUG --round N [--review] [--note=T] -- PROJECT "REQUEST"` (REQUEST = `tasks.title`) |
| plan_review | `run plan-review --round N -- PROJECT` |
| code | `run dev --round N -- PROJECT` |
| fix after review | `run dev --fix code-review --round N -- PROJECT` |
| code_review | `run code-review --round N -- PROJECT` |
| qa | `run qa --round N -- PROJECT` |
| fix after QA | `run dev --fix qa --round N -- PROJECT` |

`--round`, `--note`, `--review`, `--fix`, `--workflow` are clap flags on `Commands::Run` (hide `--round`). A manual run without `--round` computes `1 + count of same-stage runs in the current cycle` (display only; the driver always passes it). `roles::cmd_run` (`roles/mod.rs:427-469`) gains a `RunOpts` struct instead of more positional parameters.

**Starting a new task with autopilot (D-14).** The task row is created by `cmd_lead` (`lead.rs:158-166`), so the dashboard cannot start `auto TASK` before it exists. ### 3.8 Budget and pricing (D-18, D-19)

### 3.9 Kill (D-04, AUTO-05)

`cmd_kill(ctx, task_id)` (`runner.rs:55-140`) finds the task's one running run, `mark_kill_requested`, `kill_tree(root=claude pid)`, waits up to 2 s for the run row to leave `running`, else marks `killed`; with no running run it returns an error (`Task {id} không có run đang chạy ...`). The dashboard Kill calls it through `post_kill_run` (`api_runs.rs:61-173`). Extension, keeping its existing messages and exit codes for the no-driver case (`tests/runner_kill.rs` `kill_unknown_or_idle_task` expects the error):
1. If the task has a live driver (`auto_state in (running, stopping)` and `procs::alive`): first `UPDATE tasks SET auto_stop_at=now, auto_stop_kind='kill'`.
2. Then the existing path for a running run.
3. If no run is running but the driver is alive: succeed (exit 0, "Đã yêu cầu autopilot dừng"); the driver stops before the next stage. The gap is not tiny: a child spends time on git checks before `insert_run`, so also make the driver poll the kill flag while its child runs and call the same kill routine if a run appears after the flag.
4. The driver, seeing a `killed` run with `kill_requested_at`, stops with reason `dừng bởi bạn` and leaves no process: the child `run` exits by itself after `supervise` returns `Killed`.
Dashboard shutdown (D-16, `dashboard/mod.rs:259-283`): `JobManager::shutdown` sends SIGINT to job roots (the driver), waits `kill_grace_secs + 5`, then `kill_tree`. The driver forwards SIGINT to its child, records `interrupted`, exits. `kill -9` of the driver leaves a stale `running` row, shown as "đã dừng" (driver lost) and reclaimable.

## Common Pitfalls

### Pitfall 1: FK cascade eats the event log during the runs rebuild
**What goes wrong:** `DROP TABLE runs` under `foreign_keys=ON` deletes every `events` row; no error. **Why:** `events.run_id ... ON DELETE CASCADE` and `db::open` turns FK on before migrating (`db.rs:96`). **Avoid:** FK off before `BEGIN IMMEDIATE`, `foreign_key_check`, FK on after; the upgrade test asserts the event count. **Warning sign:** `events` count drops after upgrade.

### Pitfall 2: ALTER TABLE ... RENAME rewriting foreign keys
**What goes wrong:** renaming `runs` to `runs_old` first makes SQLite rewrite `events`' reference to `runs_old` (modern SQLite behaviour). **Avoid:** create `runs_new`, copy, drop `runs`, rename `runs_new` -> `runs` (the verified order).

### Pitfall 3: Driver ignores signals between runs
**Why:** tokio keeps its handler for the whole process (`signal/unix.rs:334-345`). **Avoid:** children + `libc::sigaction` flag, or install the driver's handler before any `supervise` and never rely on default actions.

### Pitfall 4: Kill lands in the gap between stages
**What goes wrong:** `cmd_kill` finds no running run, errors, and the driver starts the next stage. **Avoid:** kill flag set first; driver checks it before each stage and while the child runs (§3.9).

### Pitfall 5: Another task slips in between two stages
**What goes wrong:** `busy_reason*` sees no running run and no job reservation for a CLI-started driver; for `personal` the next stage then fails with the E-06 message. **Avoid:** live-driver rule in both busy functions and in the driver's own claim.

### Pitfall 6: Review reports counted as code changes
**Where:** `qa.rs:83-84`, `api_tasks.rs:886-887,1216-1217`, `stream.rs:6`, `planfile.rs:481-486`. **Avoid:** one shared `PROTOCOL_FILES` constant with all four report names and a helper `diff_code_names`; add a test where only a `.plan-review.md` commit follows the plan commit and `run_qa` stays disabled.

### Pitfall 7: Report committed with the wrong subject breaks plan-commit lookup
`{slug}: plan-review` is safe only because lookups use equality (`gitops.rs:171`, `api_tasks.rs:773`). Never name the commit `{slug}: plan ...` as a prefix match target, and keep tests that assert `find_plan_commit` ignores it.

### Pitfall 8: Skeleton erases the previous report the reviewer needs
Round 2 of a reviewer must see whether blocking items were addressed. Either do not pre-write a skeleton over an existing report, or tell the reviewer to read the prior report with `git show HEAD:.plan-review.md` before overwriting.

### Pitfall 9: Dev fix mode widens scope through the report
A poisoned report can name `.env` or a symlink to outside the repo; the guard canonicalises the allow list too, so a symlink named in `write_allow` would permit its target. Reject outside-root realpaths, untracked existing files and sensitive names (§3.5).

### Pitfall 10: Manual actions stay enabled while a driver sleeps between stages
`taskstate::derive` derives actions from `tasks.status` and running roles (`taskstate.rs:343-381`); with no running run, `run_dev`/`run_qa`/`relead` would be enabled during autopilot. Disable them when a driver is alive.

### Pitfall 11: Stale `auto_state='running'`
A SIGKILLed driver leaves the row. Always combine state with `procs::alive(pid,start)` (pid reuse is guarded by the start time, as `kill_never_signals_reused_pid` tests for runs).

### Pitfall 12: Budget re-check after `Chạy thêm 1 vòng`
Without the one-shot bypass the driver would stop again immediately. Persist the bypass in `auto_json` and consume it per stage.

### Pitfall 13: Fake claude cannot express a loop
One scenario file serves every invocation; a naive test would make every stage return the same report and loop to the cap. Use the by-role queue.

### Pitfall 14: Tests assert schema version 1
`tests/lib_foundation.rs:465` and the re-open check; update both to 2 in plan 01.

### Pitfall 15: `app.css` regenerated in two plans / static assets compiled in
Carried from 05.1 Pitfalls 4-5: rebuild only in the last UI plan; every UI task's verify starts with `cargo build --manifest-path agent-brain/Cargo.toml --offline --locked`.

### Pitfall 16: `--note` value starting with `-`
Pass `--note=VALUE` (one argv element) and put positionals after `--`; spawn with an argument vector, never through a shell.

    if libc::getppid() != driver_pid { return Err(std::io::Error::new(std::io::ErrorKind::Other, "driver exited before exec")); }
    Ok(()) }); }
let mut child = cmd.spawn()?;
while child.try_wait()?.is_none() { /* 200 ms: signal flag -> forward SIGINT; DB stop flags -> kill routine */ }
```

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|

| Orphaned claude processes after driver death | Availability | PDEATHSIG chain (serve -> driver -> run child), kill only by recorded PID/start time |
| Forged approval via API | Spoofing | Same token/Origin gate; approval also requires plan commit to exist; busy check before write |
