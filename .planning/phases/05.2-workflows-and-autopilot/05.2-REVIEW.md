## Critical Issues

### CR-01: The driver runs stages on whatever task branch is checked out, and Dev approves that other task's plan

**File:** `agent-brain/src/autopilot/mod.rs:308-384`, `agent-brain/src/autopilot/claim.rs:141-216`, `agent-brain/src/roles/dev.rs:260-278`, `agent-brain/src/dashboard/taskstate.rs:337-366`

**Issue:** `run_loop` computes facts from `refs/heads/<task.branch>` through `plan_commit_on_branch`, so approval and plan state are those of task A. It then spawns `run dev|code-review|qa|dev --fix` with only `-- <project>`. Every role derives the task from the **current** HEAD's `.plan.md`: `dev.rs:53-81`, `review.rs:58-86` and `qa.rs` all check `branch == meta.branch`, which is self-consistent for whatever task is checked out. No code checks `current_branch(root) == task.branch`:
- not in `claim`
- not in `run_loop`
- not in `cmd_approve`
- not in the dashboard approve path: `build_approve` has no branch check (unlike `build_auto_start`), and `approve_check` checks dirty files only when on the branch.

Here is what happens when the user is on `task/b` and runs `agent-brain auto A`, `agent-brain approve A`, or clicks **Duyệt plan** for A on an `auto` workflow:
1. Dev runs with task B's allowlist and commits on `task/b`.
2. `dev.rs:260-278` records **approval of B's plan** ("chạy Dev trực tiếp cũng coi là đã duyệt"). This bypasses B's gate, and B may still be waiting for plan review.
3. The run row gets `task_id = B`, so for A, `after <= before` and the driver stops with "run lỗi". The code changes and the approval on B stay.

The same happens if the user checks out another task branch while the driver is between stages.

**Fix:** Before every non-Plan stage, verify the branch. Also make the role refuse when the autopilot task env does not match the current task:
```rust
// run_loop, before spawn_stage (and in cmd_approve before claim):
if sr.stage != Stage::Plan
    && crate::gitops::current_branch(&root).as_deref() != Some(task.branch.as_str())
{
    let cur = crate::gitops::current_branch(&root).unwrap_or_else(|| "None".into());
    return Ok(stop_with(ctx, task_id, &task.slug, aj, run_loi(
        format!("Không ở nhánh task '{}' (nhánh hiện tại: '{cur}') — không đoán", task.branch),
        Some(&sr))));
}
// roles (dev/review/qa), after current_task():
if let Ok(want) = std::env::var(crate::autopilot::AUTOPILOT_TASK_ENV) {
    if task_id.map(|t| t.to_string()) != Some(want.trim().to_string()) {
        return Err(BrainError::error("Nhánh hiện tại không phải task của autopilot — dừng"));
    }
}
```
Also add the branch check that `build_auto_start` already has to `build_approve` when `workflow.auto`.

## Warnings

### WR-01: A terminal Ctrl+C reaches the stage child twice, so a graceful stop always becomes SIGKILL (known item 1)

**File:** `agent-brain/src/autopilot/mod.rs:167-180, 213-222`; `agent-brain/src/runner.rs:337-353`

**Issue:** The stage child stays in the driver's process group on purpose, so a terminal Ctrl+C delivers SIGINT to both. The driver's handler sets `SIGNALED`, and within 200 ms the loop forwards **another** SIGINT to the child. In `supervise_async`, the second SIGINT takes the `else if !force` branch: `force = true`, "Dừng ngay (SIGKILL)".

Every interactive Ctrl+C therefore skips the `kill_grace` period:
- claude never writes its `result` event.
- The run ends `killed` with `usage_source partial` and `cost_usd 0`, and the budget falls back to token estimates.
- Any in-flight file write is cut.

**Fix:** Forward SIGTERM instead of SIGINT. The runner's SIGTERM arm only starts the graceful stop and never escalates. Alternatively, forward only when the child did not get the terminal signal, for example by putting the child in its own process group and always forwarding.
```rust
libc::kill(child_pid, libc::SIGTERM);
```

### WR-02: Lead failures after the run are recorded as success, and the driver ignores the child's exit code, so Lead re-runs with no round cap (known item 7)

**File:** `agent-brain/src/roles/lead.rs:324-359`; `agent-brain/src/autopilot/mod.rs:61-67, 372-383`; `agent-brain/src/autopilot/decide.rs:574-583`

**Issue:** When the claude run itself succeeds, `cmd_lead` can still fail after `execute_role_staged`:
- `.plan.md` is missing (324-328)
- `validate_plan` errors (337-350)
- `commit_paths` fails, for example a pre-commit hook rejects the commit (359)

Each of these returns `Err` without `set_run_outcome`, so the run row stays `succeeded` with outcome NULL, and `RunFact::is_ok()` is true. The driver discards `ChildOutcome.exit_code` (`#[allow(dead_code)]`) and only checks that a run row was created.

On round 1 there is still no plan commit, so `plan_phase` rule (a) returns `Plan { round: 1 + highest_ok_plan_round }` with **no `max_rounds` check**. Lead (opus) runs again from a fresh skeleton. This repeats until the budget or `MAX_STAGES_PER_RUN = 50` stops it. With the default $20 / 60 min, that is many wasted Lead runs.

**Fix:** Do both of the following:
- Record these failures, for example `set_run_outcome(run_id, "protocol_violation")` (or a new `lead:invalid_plan`) before each `Err` after the run, so D2 stops with a clear reason.
- In `spawn_stage`, return `exit_code`. In `run_loop`, stop with `run_loi(first_err_line)` when the code is not 0, 1-with-outcome or `EXIT_BLOCKED`/`EXIT_PROTOCOL`, and the newest run has no outcome.

Also cap rule (a): `if 1 + highest_ok_plan_round > wf.max_rounds + grant { Stop(HetVong) }`.

### WR-03: A replan after the build or QA loop continues the plan round count into the new cycle, and grants carry over

**File:** `agent-brain/src/autopilot/decide.rs:850-878` (`rule_d3_replan`), `agent-brain/src/autopilot/mod.rs:350-355`

**Issue:** Here is the sequence:
1. In cycle 1, `D3` computes `round = 1 + highest ok plan round` over the **current** cycle, which is the cycle *before* the new Plan run.
2. After the build or QA loop, "Chạy lại Lead" or "Trả về Lead" on an `auto` workflow runs `auto N --replan`. The new Plan run starts cycle 2 (see `cycles()`) but keeps round 2, 3, 4… (stored via `--round`).
3. In cycle 2, `plan_phase` compares that stored round with `max_rounds + grant`. After one `revise`, the autopilot stops with "hết vòng" (for example "3 / 3 vòng" after a single review of the new plan).

Meanwhile Implement and QA restart at round 1 in the new cycle (D6/D7 `None`, `round: 1`). That contradicts O7 ("round = 1 + same-stage runs in the current cycle"). `aj.grants.clear()` only fires when `sr.round == 1`, so grants from cycle 1 also leak into cycle 2.

**Fix:** In `rule_d3_replan`, start at round 1 when the last run's loop is Build or Qa, because the replan opens a new cycle:
```rust
let opens_new_cycle = matches!(f.runs.last().and_then(loop_of), Some(Loop::Build | Loop::Qa));
let round = if opens_new_cycle { 1 } else { 1 + highest_ok_plan_round };
```
Rule (a) and the gate logic need the same change. Add a decide test: P1, PR1 approve, implement, code review pass, QA fix×3 → replan, then revise → expect `Plan round 2`, not a stop.

### WR-04: Control and release writes are not tied to the state they were checked against

**File:** `agent-brain/src/autopilot/claim.rs:219-224`; `agent-brain/src/dashboard/api_tasks.rs:1652-1686, 1688-1720, 1738-1742`

**Issue:** `post_control` reads the state with `load_task_state`, checks `rev` and the control, then writes in separate statements. Nothing re-checks the state at write time. There are four problems:
1. **`claim::release`** issues three separate `UPDATE`s, with no transaction and no `WHERE auto_pid = <own pid>`. `auto_end` (1740) calls it on a task the handler saw as `stopped`. Here is the race:
   1. A CLI `auto N` (or a second tab) claims the task between `load_task_state` and `release`.
   2. `release(..., "ended")` overwrites `auto_state = running` and NULLs the live driver's pid.
   3. `driver_alive` is now false, so a second `auto N` can claim the same task while the first driver still runs.

   The same three-statement window exists when a driver releases while another process claims.
2. **`return_lead`** (1690) clears the approval *before* `start_job`. If `start_job` fails (409 busy, 503 shutting down), the approval is gone and nothing runs. `busy_reason_for_task` skips the reservation when a job of *this* task is still running (285-296), so this is reachable while the previous job for the task is exiting.
3. **The `approve` revert** (1662-1672) restores the snapshot taken before the load. If two approvals race (CLI and dashboard), the failed one erases the successful one, and the driver it started stops at the gate.
4. `rev` itself is optional (IN-07).

**Fix:**
- Make `release` one conditional statement in a transaction: `UPDATE tasks SET auto_json=?1, auto_state=?2, auto_pid=NULL, auto_pid_start=NULL WHERE id=?3 AND (auto_pid IS ?4)`, passing the caller's own pid, or NULL for `auto_end`.
- For `auto_end`, add `AND auto_state='stopped'` and return 409 `stale` when 0 rows change.
- In `return_lead`, start the job first and clear the approval only on success (or restore it on failure, as `approve` does).
- Make the approve revert conditional: `... WHERE approved_commit = <plan_commit just written>`.

### WR-05: A review report template is left in the tree when the reviewer is killed or fails, and it blocks Lead and Dev (known item 5, broadened)

**File:** `agent-brain/src/roles/review.rs:200-214` (template written before `execute_role_staged` at 250), 253-279; `agent-brain/src/roles/lead.rs:156-167`; `agent-brain/src/roles/dev.rs:83-95`

**Issue:** The skeleton `.plan-review.md` / `.code-review.md` is written before the run. Every later `Err` path leaves it in the tree:
- E-06 refusal and "claude not found" inside `execute_role_staged`
- timeout, kill or failure
- non-zero exit

On round 1 there is no committed copy, so the file is untracked. It survives `checkout`, as the live check saw. The review role tolerates its own file in the dirty check, but Lead (`dirty.remove(".plan.md")` only) and Dev (no exceptions) do not. After a killed review, these all fail with "Working tree có thay đổi chưa commit":
- **Trả về Lead** is disabled (`build_return_lead` lists the dirty file).
- Approve then Implement stops with "run lỗi".
- A manual relead fails too.

**Fix:**
- Write the skeleton only after the busy and E-06 checks.
- On every `Err` or killed path, restore the report. Use `git checkout -- <file>` when it is tracked at HEAD; otherwise remove the file, but only if it still equals the skeleton.
- Alternatively, let Lead and Dev's dirty checks ignore an untracked report that equals the skeleton.

### WR-06: Reviewer and QA reports can widen Dev fix-mode write scope to CI, hook and build-script files with no user approval

**File:** `agent-brain/src/report.rs:258-310`; `agent-brain/src/roles/dev.rs:159-183`

**Issue:** In fix mode, the write allowlist is plan files ∪ `named_files(report)`. Both front-matter `files` and **any backticked token** in the body that looks like a path count. The report is LLM output written after reading untrusted repo content. In autopilot, the fix stage runs with no human in between, after the plan was approved but not the report.

The sensitive deny-list has gaps:
- It covers `.env*`, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*` and `.claude`.
- It matches case-sensitively.
- It allows tracked or new paths that execute code or leak secrets later: `.github/workflows/*.yml`, `.gitlab-ci.yml`, `.husky/*`, `.githooks/*`, `.gitmodules`, `.gitattributes`, `Makefile`, `package.json` (lifecycle scripts), `.npmrc`, `.vscode/*`, `.devcontainer/*`.

For example, a prompt-injected `.code-review.md` that names `` `.github/workflows/ci.yml` `` lets the fix run edit CI. agent-brain itself commits with `git commit` (`commit_paths`), so hooks configured through `core.hooksPath` paths also run. This follows D-12 and RESEARCH §3.5 as written, but the threat model's intent ("cannot widen scope") is not met.

**Fix:**
- Extend the deny-list, case-insensitively, with the CI, hook and editor directories above.
- Only accept body tokens for files that already appear in the diff since the plan commit (`diff_code_names(plan_commit, HEAD)`); keep front-matter `files` as the only way to name a new file.
- Print the widened set in the stop or ledger line so the user sees it.

### IN-02: A manual `run lead` stores round NULL (known item 3)

**File:** `agent-brain/src/roles/lead.rs:280-284`; `agent-brain/src/main.rs:45-47`
**Issue:** `--round` is hidden and only the driver passes it. A manual first Lead gets NULL, and `effective_rounds` derives 1, so display and decisions are right today. But stored and derived rounds then mix in one cycle, and any reader of `runs.round` other than `effective_rounds` (stats, exports) sees NULL.
**Fix:** When `opts.round` is None, compute it with `decide::effective_rounds` over the task's runs plus the new run, and store it. Or document that NULL means "derived".

### IN-03: The duplicate "Đã duyệt plan … (task N)." line cannot be reproduced from the code (known item 4)

**File:** `agent-brain/src/autopilot/mod.rs:640-645`
**Issue:** `cmd_approve` emits the line once, on stderr, and no other code path prints that text. The duplicate seen in 05.2-20 most likely comes from how output was captured (stderr and a tee, or a job echo). No CLI test asserts the line count.
**Fix:** Add an assertion in `tests/autopilot_kill.rs::approved_nhanh_task` that `stderr.matches("Đã duyệt plan").count() == 1`. If the test passes, close the item as a capture artifact.

### IN-04: `decide.rs` is 3041 lines, and some fields and return types are dead (known item 6)

### IN-05: A "hết vòng" stop shows the cap without the grants

**File:** `agent-brain/src/autopilot/decide.rs:630, 991, 1109`; `agent-brain/src/autopilot/view.rs:42-62`
**Issue:** The decision uses `cap = max_rounds + grant`, but `StopInfo.cap` stores `wf.max_rounds`. After one "Chạy thêm 1 vòng", the next stop reads "… sau 4 / 3 vòng."
**Fix:** Store the effective cap (`cap` local) in `StopInfo.cap`.

### IN-06: The "run lỗi" detail is the child's first stderr line, which is often the role banner rather than the error

**File:** `agent-brain/src/autopilot/mod.rs:184-206, 376-381, 544-546`
**Issue:** `execute_role_staged` prints `[agent-brain] dev · <project> · profile …` before `supervise`. When the spawn then fails (claude binary missing, run dir error), no run row exists. The stop detail is then the banner, not the error. Warnings such as "Cảnh báo workflows.json: …" have the same effect for Lead.
**Fix:** Keep the **last** non-empty stderr line, or the first line that does not start with `[agent-brain]` or `Cảnh báo`.

### IN-07: `rev` is optional on control endpoints, and task polling has no sequence guard

**File:** `agent-brain/src/dashboard/api_tasks.rs:40-57, 1626-1633`; `agent-brain/assets/dashboard/js/task.js:55-58, 70-112`
**Issue:**
- A body without `rev` (or `rev: null`) skips the stale check entirely.
- `load()` fires every 3 s with no in-flight flag or sequence number (unlike `loadPipeline`). `get_task` runs several `git` processes on a 2-worker runtime, so a slow server lets polls pile up and land out of order. A poll sent before a successful control can overwrite the fresh state and show the old buttons again. `rev` then refuses the click, but the user sees a 409.

**Fix:**
- Make `rev` required (`rev: String`) for control bodies.
- Give `load()` the same `_seq` / busy pattern as `loadPipeline`, and drop responses older than the last applied one.

### IN-08: Dashboard Kill and the driver can both call `cmd_kill` on the same run

**File:** `agent-brain/src/runner.rs:63-114`; `agent-brain/src/autopilot/mod.rs:223-240`
**Issue:** `cmd_kill` sets the task's kill flag (line 67) before it marks `kill_requested_at` on the run (114). A driver poll that lands in between sees the flag with no `kill_requested_at` and starts its own `cmd_kill`. The result is two `kill_tree`s, two "Đang dừng" lines, and the driver loop blocked for grace plus 2 s. It is harmless today, because both send SIGTERM and then SIGKILL, but it depends on timing.
**Fix:** In `cmd_kill`, call `mark_kill_requested` before `request_auto_stop`. Or make the driver skip `cmd_kill` when the flag's `auto_stop_at` is newer than its last poll.

### IN-09: Roles still find the plan commit with the unbounded `git log HEAD` scan that 05.1 WR-01 fixed elsewhere

**File:** `agent-brain/src/gitops.rs:240-256` (`find_commit_by_subject`), used at `roles/review.rs:103`, `roles/qa.rs:74`, `roles/dev.rs:265`
**Issue:** The driver, `approve_check` and the dashboard use `plan_commit_on_branch` (bounded by `base_commit`, `refs/heads/…`, `--`). Dev's auto-approval, review and QA scan all of HEAD's history for `"{slug}: plan"`. A reused slug can match a merged plan commit from an older task. The two sources can then disagree on which commit was approved.
**Fix:** Use `plan_commit_on_branch(root, &task_row.branch, &slug, task_row.base_commit)` in the roles whenever `current_task` returns a row. Keep `find_commit_by_subject` only as a fallback.

### IN-10: From the CLI, a manual run on a non-personal project is not blocked while a driver is between stages

**File:** `agent-brain/src/roles/mod.rs:296-341`
**Issue:** The E-06 live-driver check runs only for the `personal` profile. On `work` projects, `agent-brain run dev|lead …` started from a terminal while a driver of the same project is between stages gets only a warning. Two claude processes then write to one working tree. README documents this, and the dashboard blocks it (`busy_reason`), but together with CR-01 it is a second route to cross-task writes.
**Fix:** Apply `live_driver_reason(conn, &project.id, &project.profile, exclude)` for every profile, excluding the driver's own task through `AGENT_BRAIN_AUTOPILOT_TASK`.
